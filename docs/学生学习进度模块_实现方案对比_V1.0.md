| 项 | 结论 |

## 1 需求边界与硬约束

### 1.1 需求

在自学平台内新增一个「学生学习进度」窗口或模块，采集学生的学习进度数据，并可靠地传递给考试平台（用于随堂测试准入判定）。

拆开是两件事，容易被混为一谈：

1. **采集**：进度从哪来、按什么口径算、粒度多细；
2. **传递**：谁主动（推/拉）、多快（实时/分钟/日）、多可靠（丢了怎么办）、谁说了算（哪个值是权威）。

### 1.2 文档给出的硬约束

| # | 约束 | 出处 | 对方案的约束力 |
| --- | --- | --- | --- |
| C1 | 准入判定由考试平台调 `GET /completion/{userId}/{courseId}`，**标 ★ 且"不回写"** | 6.3 第 5 项 | 必须有一个**服务端权威事实源**，且可被随时回源 |
| C2 | 跨平台通道只允许发事件目录内类型；`lesson.completed`、`note.*` 属本地扩展，必须**与正式通道隔离** | 8.1 纪律 | 进度中间态事件不能混在正式通道里推 |
| C3 | 事件必须携带完整封套（`eventId`/`eventVersion`/`sourcePlatform`/`actorId`/`correlationId`/`requestId`） | 8.2 | 推送方案需要事件组装层 |
| C4 | 写操作必须带 `Idempotency-Key`，网关按该键去重 | 5.2 / 6.3 第 6 项 | 推送必须支持幂等重放 |
| C5 | 章节进度上报属**高频**接口，允许 5s 节流 | 6.3 第 7 项 | 不宜"每 5 秒向考试平台推一次"，必须聚合 |

> C1 + C2 基本已经决定了推荐方向：**权威值在服务端，中间态用拉，完成态用推。**

### 1.3 先把「进度」定义清楚

"进度"不是一个数，而是三层口径。方案选型本质是在选"采集到第几层"。

| 层级 | 指标 | 数据来源 | 精度 | 采集成本 |
| --- | --- | --- | --- | --- |
| L1 课程级 | 完成度 %、已完成/总课时、累计时长、是否完成 | `course_user`、`chapter_user`（已落库） | 口径统一、可复算 | 极低（现有数据直接派生） |
| L2 章节级 | 每章是否完成、最近学习章节、断点位置 | `chapter_user.position/duration` | 中 | 低（现有表已有字段） |
| L3 行为级 | 心跳、播放/暂停/seek、切后台、有效时长 | 需前端埋点，**当前无采集** | 最细 | 中高（要新增埋点 + 反作弊） |

平台既有完成规则：**课时观看 ≥30% 记为完成**，课程进度 = 已完成课时 / 总课时。L1 口径沿用此规则，不另造一套。

## 2 方案 A：窗口式（后端派生 + 发件箱推送 + 回源兜底）

> 已实现，线上可运行。

### 核心思路

学习行为照旧落库（`chapter_user` / `course_user`），进度窗口只是**读模型 + 操作入口**，本身不产生新数据。进度变化时在**同一事务**里写一条"待发送事件"到发件箱表 `kg_exam_outbox`，由定时任务/即时触发经网关投递到考试平台。考试平台若对实时值存疑，随时用 `GET /completion` 回源。

数据流：

```
学习行为 → 落库(chapter_user/course_user) ─┬→ 窗口读取（学生看到什么）
                                          └→ 同事务写 outbox ──→ 投递器 ──→ 网关 ──→ 考试平台
                                                                  ↑
                                            考试平台 GET /completion ← 回源（权威值）
```

### 数据采集方式与范围

- **方式**：后端派生（读现有表计算），非侵入式，不改学习行为本身。
- **范围**：L1 全量 + L2 的"最近学习章节/课时数"；不含 L3 行为埋点。
- **触发**：课时完成落库后入箱；进度单调递增 + 5 个百分点节流（避免每看一节课推一次）；课程首次完成时额外发 `course.completed`（去重）。
- **落库即事实**：事件 payload 在入箱时固化快照，之后即便原表变化，也能复现"当时推了什么"。

### 适用场景

- 五平台联动联调、答辩/路演演示；
- 考试准入判定（低频、强一致优先）；
- 上游数据已在库、不想改动学习主流程。

### 优点

1. **单一事实源**：进度只有一处算法，页面、接口、推送三者同源，不会出现"页面显示 80%、考试平台收到 60%"。
2. **可靠性工程成本最低**：事务性发件箱 + 唯一键幂等 + 指数退避 + 死信 + 手动重放（`exam_sync replay`），这套模式不需要任何中间件。
3. **对下游弱依赖**：考试平台挂了不影响学生学习，事件在 outbox 里等着，恢复后自动补发。
4. **可回源、可对账**：`event_id` + `payload` 落库，随时能回答"这条数据什么时候推的、推了什么"。
5. 与接入说明的接口清单天然对齐（`/progress`、`/completion`）。

### 缺点

1. **非实时**：分钟级（定时器粒度），不满足"学生刚看完就立刻判准入"的极端场景（可通过页面按钮即时触发缓解）。
2. **只能覆盖平台已知的行为**：平台没记录的学习（线下、第三方课程）无法体现。
3. **中间态事件与 C2 有摩擦**：`learning.progress.updated` 不在事件目录内，直接推正式通道会触发下游"未知主版本"隔离告警，需要改造（见第 9 节 R1）。
4. 需要维护一张 outbox 表与一个投递任务，运维面比"纯查询接口"大一点。

### 实现成本与可维护性

- 成本：**3～4 人日**（新增模型/仓储/服务/控制器/任务/迁移共 15 个文件；本次已完成约 3/4）。
- 可维护性：**高**。口径集中在一个 `Progress` 服务，事件契约集中在 `Gateway` 一处，新增事件类型只改一处；缺点是 outbox 表会长期增长，需要归档策略。

## 3 方案 B：前端埋点直报（窗口内嵌 SDK / 轻量上报）

### 核心思路

在课程播放页和进度窗口内嵌一段 JS，学习行为发生时（心跳 15s、暂停、切后台、seek）直接向网关或平台轻接口上报，考试平台拿到的就是"行为流"。窗口退化为**实时看板**。

### 数据采集方式与范围

- **方式**：浏览器端埋点，客户端计时。
- **范围**：L3 行为级（最细），可算"有效学习时长"（剔除挂机、切后台）。
- **通道**：页面 → 网关（需处理跨域、令牌续期）或页面 → 平台轻接口 → 网关。

### 适用场景

- 需要防挂机、精细学情分析、学习行为画像；
- 后端无改造预算、想快速验证；
- 前端为主的产品（多端 H5/小程序）。

### 优点

1. **实时**（秒级），窗口体验最好；
2. **粒度最细**，"有效学习时长"这类指标只有前端能算准（后端只知道"看过了"）；
3. 前端改造量小、上线快。

### 缺点

1. **数据不可信**：明文上报、可篡改、可脚本伪造；断网/关标签页直接丢事件；**不能作为考试准入依据**（与 C1 冲突）。
2. **双源冲突**：前端算一套、后端派生一套，两边对不上时无法裁决。
3. **契约成本被低估**：跨域、CSRF、令牌续期、网关限流（高频接口 5s 节流）都要前端处理，出错面反而更大。
4. 用户清理缓存/换设备后状态不一致。

### 实现成本与可维护性

- 成本：**2～3 人日**（前端为主）。
- 可维护性：**中低**。埋点点位分散在多个页面，口径随页面改版漂移；多端（PC/H5/小程序）要重复实现三遍。

## 4 方案 C：服务端批量汇总（T+1 快照 / 对账）

### 核心思路

夜间定时任务全量计算"每个学生 × 每门课"的进度快照，写入宽表（或按批生成对账文件），考试平台按批拉取或接收批量推送。窗口展示的是**昨日快照**。

### 数据采集方式与范围

- **方式**：离线 ETL / 定时聚合，全表扫描或增量游标。
- **范围**：L1 + L2 全量，可扩展班级/院系/专业维度聚合。
- **通道**：批量接口（分页）或文件（对象存储 + 签名 URL）。

### 适用场景

- 排考、批量准入名单（一次几千人，不需要秒级）；
- 学情报表、督导看板、期末统计；
- 作为方案 A 的**每日对账兜底**（补漏、发现口径偏差）。

### 优点

1. **成本低、口径统一**、对上游零侵入；
2. 天然可对账：两份快照 diff 就能发现漏推/错推；
3. 适合大批量、可重跑（幂等覆盖写）；
4. 不依赖实时链路，运维简单。

### 缺点

1. **延迟小时级（T+1）**，无法支撑"学完立刻考试"；
2. 全量扫描对数据库有压力，大表需要游标分片；
3. 快照是"过去时"，学生当天新学的进度看不到。

### 实现成本与可维护性

- 成本：**3～5 人日**（含批处理接口/文件格式约定、调度、对账脚本）。
- 可维护性：**高**。纯读、可重跑、无状态，出问题重跑一次即可，不产生脏数据。

## 5 方案 D：实时事件流（消息总线订阅）

### 核心思路

每次进度变化写消息队列（Kafka / RabbitMQ / Redis Stream），考试平台作为消费者订阅 topic；网关注册 topic 与权限，多个消费方（考试、教务、督导大屏）各自消费。

### 数据采集方式与范围

- **方式**：应用内埋点 → MQ 生产；消费端维护位点。
- **范围**：全事件流（含中间态心跳），支持回放。

### 适用场景

- 秒级要求 + **多个**消费方（≥2）；
- 高并发、需要削峰；
- 需要事件回放做审计/重算。

### 优点

1. 实时性最好；2. 生产消费彻底解耦，加消费方不用改生产方；3. 可回放、可审计；4. 天然削峰。

### 缺点

1. **成本最高**：MQ 部署/运维、消费位点、顺序性、重复消费、死信队列、监控告警，全都要自己扛；
2. 考试平台必须**改造消费端**，联调面从"调一个接口"变成"接一个消费者"，跨团队协调成本高；
3. 只有一个消费方时属**过度设计**（用 outbox 已达同等可靠性）；
4. 与 C2 的事件目录纪律冲突更直接——MQ 上乱发类型，下游隔离告警会更多。

### 实现成本与可维护性

- 成本：**8～15 人日** + 持续运维。
- 可维护性：**中**。职责清晰但架构复杂度显著上升；小团队容易出现"没人敢动"的组件。

## 6 方案 E：纯拉模式（考试平台主动回源，平台不推）

### 核心思路

平台只提供只读接口（`GET /progress/{userId}`、`GET /completion/{userId}/{courseId}`），完全不主动推。考试平台在自己需要时按需调用，本地做短 TTL 缓存。

### 数据采集方式与范围

- **方式**：与方案 A 相同的服务端派生（复用同一套算法），只是去掉 outbox 与投递器。
- **范围**：L1 + L2 明细查询，按需。

### 适用场景

- 平台方不愿承担投递可靠性责任（"数据我给你，什么时候取你决定"）；
- 考试平台自己有定时任务/缓存层；
- 联调初期最小可用版本（1～2 天可交付）。

### 优点

1. **最省事**：无 outbox、无调度、无重试，接口幂等天然成立；
2. 永远不会"推错数据"——对端每次拿到的都是当前值；
3. 与 C1 完全一致（`completion` 本就是拉接口）。

### 缺点

1. **考试平台承担实时性压力**，需要自己轮询、自己缓存、自己防雪崩；
2. 平台无法感知"谁在取、取了多少"，缺少可观测性；
3. 无法满足"完成即通知"的事件驱动场景（如自动开考、消息推送）。

### 实现成本与可维护性

- 成本：**1～2 人日**。
- 可维护性：**高**（只读、无状态），但把复杂度转移给了对端。

## 8 推荐结论与依据

### 推荐：以 A 为主干，C 做对账，E 的 completion 做准入权威

不是"选一个"，而是**分工**：

- **A 负责"通知"**：课程完成、进度变化经 outbox → 网关 → 考试平台；
- **E 的 `completion` 负责"裁决"**：考试平台判准入前回源一次，不用缓存值、不用推送值；
- **C 负责"兜底"**：每日全量对账，发现漏推/口径偏差自动补推。

### 四条依据

1. **契约倒逼**：C1 明确准入判定走 `GET /completion` 且"不回写"——这要求服务端有权威值，A/E/C 都满足，**只有 B 不满足**（前端数据不可采信）。
2. **C2/C5 排除"高频推"**：事件目录只认 `course.completed`，章节上报允许 5s 节流——说明设计意图就是"完成态推送 + 明细态查询"，不需要把每个心跳都推出去，**方案 D 因此缺少必要性**。
3. **单消费方 + 低频判定，稳定性 > 实时性**：考试准入不是秒杀场景，分钟级完全够用；而 outbox 的成本约等于零却换来完整可靠性，性价比最高。
4. **可渐进演进**：A 的 outbox 是"最小可靠前提"，将来真出现第二个消费方，把投递器换成 MQ 生产者即可，采集层与口径层不动——**A 是 D 的子集，不会白做**。

### 什么情况下应该改选

| 若出现…… | 则应转向 |
| --- | --- |
| 需要"学完 1 秒内自动开考/推送提醒" | D（或 A + WebSocket 通知，仅对在线用户） |
| 上线防挂机、有效学习时长考核 | B（仅作行为分析，仍不作准入依据） |
| 考试平台要求"每天一份全量名单" | C 独立成线，与 A 并行 |
| 平台方明确"不做投递，只提供数据" | E |

## 9 主要风险点与对策

| # | 风险 | 影响 | 对策 |
| --- | --- | --- | --- |
| R1 | **事件类型越界**：`learning.progress.updated` 不在 8.1 目录内，走正式通道会被下游按"未知主版本"隔离告警 | 考试平台收不到进度中间态，甚至触发告警工单 | 中间态改为**走 `GET /progress` 回源**，正式通道只发 `course.completed`；若确需推，则开**独立 endpoint/topic** 与正式通道隔离（当前实现两者同通道，需收口） |
| R2 | **口径漂移**：平台"≥30% 算完成"与考试平台自己的判定不一致 | 出现"平台说完成了、考试平台不让考" | 契约里带 `ruleVersion`（现为 `v1`），completion 响应回显；双方以该版本为准，改规则必须升级版本号 |
| R3 | **乱序/重复**：同一课程多条进度事件乱序到达、网络重试导致重复 | 进度被回退、重复统计 | 发送端 `event_id` 唯一键 + 幂等键；消费端按 `progress` 取 max、按 `occurredAt` 判新旧，禁止直接覆盖 |
| R4 | **网关不可用导致堆积** | 进度延迟，长时间堆积后一次涌入打爆对端 | 指数退避（1s→1h）+ 死信 + **outbox 堆积量监控告警**（当前缺，需补）；补发限速 |
| R5 | **身份映射缺失**：内部 `user_id` 与 OIDC `sub`（`usr_xxx`）映射不上 | 数据串号或静默丢弃 | 对外只用 `sub`，内部 ID 不出网；映射不到时返回 404 契约错误，**绝不兜底默认值** |
| R6 | **隐私与最小化**：学习时长、行为轨迹属个人信息 | 合规风险 | 只传课程级聚合（完成度/课时数/时长），不传播放位置、IP、设备指纹；明确留存期；页面仅本人可见 |
| R7 | **准入误判**：考试平台用缓存的旧值判准入 | 该考的没考、不该考的进了 | 一律以 `completion` 实时回源为准，对端缓存 TTL ≤60s，缓存仅用于展示 |
| R8 | **把 B 的数据当准入依据** | 可被脚本刷进度绕过考试 | 前端数据只进分析库，打 `trust=low` 标记，禁止参与准入 |
