## 二、三步接入

### 第 1 步：取 AppSecret

```bash
ssh root@8.138.246.181 \
  "python3 -c \"import json;d=json.load(open('/etc/jingyuan-gateway/secrets.json'));print(d['app_keys']['jy-learning-svc']['secret'])\""
```

同时确认网关路由白名单里确实有这个键（文档第 159 行说已预置，但仍需眼见为实）：

```bash
ssh root@8.138.246.181 "grep -n 'account-verify' -A 6 /root/gw-deploy/configs/routes.py"
```

期望看到该路由的 `l2([...])` 列表内含 `jy-learning-svc`。若不在，需网关管理员补上——但**不要自行修改 `routes.py`**，那属于网关方责任范围。

### 第 2 步：写入本平台配置

在服务器上就地注入，密钥不落命令行历史：

```bash
./apply_forum_peer.sh --config /www/ctc/config/config.php --secrets /etc/jingyuan-gateway/secrets.json
```

该脚本会：
1. 从 `secrets.json` 读 `app_keys["jy-learning-svc"].secret` → 写入 `gateway.app_secret`
2. 读 `internal_sign_keys["learning"]` → 写入 `gateway.internal_sign_secret`
3. 写前备份、写后 `php -l` 校验，语法不过自动回滚

**`internal_sign_secret` 也要一起给。** 它不是给账号确认用的，而是投递链路的强制门槛：为空时出站直接拒发，返回 `internal_sign_secret_missing`。

清缓存后生效（opcache 有 2 秒延迟，改完立刻请求会读到旧配置）：

```bash
redis-cli -n 3 eval "local ks=redis.call('keys','_PHCR_ANNOTATION_:*'); for i,k in ipairs(ks) do redis.call('del',k) end; return #ks" 0
rm -f /www/ctc/storage/cache/volt/*.php
systemctl reload php-fpm
sleep 3
```

### 第 3 步：验证

**第一层：先证明密钥本身对**（用论坛方自己的脚本，排除我方代码干扰）：

```bash
python3 account_verify_client.py <论坛账号> '<密码>' jy-learning-svc
```

**第二层：再跑我方合规验收**：

```bash
python3 verify_account_link.py --group gateway \
        --secrets /etc/jingyuan-gateway/secrets.json \
        --login <论坛账号> --password '<密码>'
```

A 组 10 条，重点看三条：

| 用例 | 期望 | 含义 |
| --- | --- | --- |
| A5 密钥有效性 | 200 | 密钥对了，后面才值得看 |
| A7 错误密码 | 401 + `40104` + `invalid_credentials` | 防枚举口径一致 |
| A9 正确凭据 | 200 + `confirmed: true` | 链路真正打通 |

**第三层：页面验证**——登录页出现「论坛账号」标签，用真实账号登录成功，且首次登录后 `kg_account.forum_uid` 有值。

## 三、失败码对照

按文档第四章整理。**只有 40104 与用户输入有关，其余都是接入问题，不要提示用户「密码错误」。**

| 码 | 含义 | 排查方向 |
| --- | --- | --- |
| `40105` | 签名头缺 / 算法不符 / 签名不一致 | 对照 canonical 七段；确认 `X-Sign-Alg: HMAC-SHA256`；确认 body 未经二次编码 |
| `40106` | 时间戳超 ±300s | 服务器校时（`chronyc tracking`），偏移 >30s 即告警 |
| `40107` | nonce 重复 | 每次请求必须重新生成；Redis `SET NX EX 600` |
| `40108` | AppKey 未登记或停用 | 核对 `jy-learning-svc` 拼写与网关白名单 |
| `40001` | 参数非法 | `login` 1–100 字符、`pass` 8–32 字符、`login_type ∈ {auto,username,email}` |
| `41300` | 体积超 64 KB | 正常请求不会触发，出现即检查是否误传了附件 |
| `40300` | 未登记路由 | 网关 `routes.py` 缺 `account-verify`，找网关管理员 |
| `40303` | 绕过网关直连 / 内部签名伪造 | 检查是否误配成直连 9088 |
| `42901` | 限流 | 200 QPS/AppKey、60 QPS/IP；按 `Retry-After` 退避 |
| `40104` + `invalid_credentials` | **账号或密码错误** | 唯一该提示用户的失败 |
| `40104` + `account_unavailable` | 账号停用/删除 | 提示联系管理员 |
| `50200` / `50400` | 上游不可达 / 超时 | 网关到论坛 9088 这一跳；稍后重试 |
| `50000` | 论坛内部错误 / 配置缺失 | 带 `requestId` 反馈运维，查 `journalctl -u jingyuan-wechat \| grep account-verify` |

## 四、已完成的验证（不需要密钥即可复跑）

### 4.1 签名基准对拍

与本平台 PHP 实现对比论坛方 `account_verify_client.py` 的 `sign()`：

**5/5 一致**，覆盖 ASCII、中文、`\u` 转义、含斜杠、空 body。

### 4.2 出站链路端到端（关键）

前一项只证明「签名函数算得对」。这一项证明**实际发出的 HTTP 请求能被验签方接受**——curl 有没有真的带上头、body 是否与签名时逐字节一致、path 是否与签名时相同。

做法：起一个按文档规范独立实现验签的本地网关，让真实的 `GatewaySign::headers()` + 真实 curl 打过去。

```bash

```

## 五、一处有意为之的偏差

文档标注接口超时为 **3s**（S 级）。本平台配的是 **5s**（`gateway.account_timeout`）。

原因：3s 是「网关 → 论坛」这一跳的预算，本平台到网关还有一跳。客户端超时若要等于服务端超时，会在网关尚未返回时先断开，把「对端慢」误报成「网关不可达」。5s = 3s 网关预算 + 余量，注释已写在配置里。
