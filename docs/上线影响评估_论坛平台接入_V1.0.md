## 三、对现有功能的影响

### 3.1 入站鉴权：从"无校验"变成"两套校验"

`beforeExecuteRoute` 的五条分支，当前与目标状态的行为差异：

| 分支 | 条件 | `verify_sign=false`（现在） | `verify_sign=true`（目标） |
| --- | --- | --- | --- |
| 1 用户态 | `ok && userId != ''` | 任填 `X-User-Id` 即通过 | 需网关签名覆盖七个字段 |
| 2 网关服务态 | `ok && mode == 'service'` | **任填 `X-Auth-Mode: service` 即通过** | 需网关签名 |
| 3 对端直连 | `PeerAuth` 成功 | 需 `X-App-Code` + 签名（secret 空则失败） | 同左 |
| 4 握手 | 路径匹配 | 放行 | 放行（设计如此） |
| 5 本地兜底 | `ok && appCode == ''` | 放行 | **不再放行** |

关键点：分支 2 的代码注释写明"安全性依据：走到这里说明 TrustedHeader 已按 `gateway.verify_sign` 校验过内部签名"。这句话在 `verify_sign=false` 时不成立，而 `X-Auth-Mode` 是客户端可控头。这是当前唯一的实质安全缺口。

### 3.2 出站投递：结课事件开始 fanout

`course.completed` 目前被三个对端订阅，其中 `training` 已停用：

| 对端 | enabled | base_uri | 实际行为 |
| --- | --- | --- | --- |
| exam | true | 空 | 本地直连模式，`send()` 直接返回成功（演示态） |
| forum | true | `http://8.138.246.181` | **真实外发** |
| training | false | 空 | 不投递 |

影响：一名学生结课，`exam_outbox` 从 1 条变 2 条。写放大 2 倍，绝对量取决于结课频次，属低频事件，DB 压力可忽略。

### 3.3 失败态可见性变化

`forum.app_secret` 为空时，`Gateway::send()` 在**发请求之前**返回 `gateway_app_secret_missing`。因此：

- 不会产生任何外网流量（这一点容易被误解为"已经接通了"）
- 但事件会按退避策略累计重试，最终进死信
- 页面「死信」计数会持续上涨，属于配置缺失的正常表现，不是代码缺陷

重试节奏（`Sync::BACKOFF = [1, 5, 30, 120, 600, 3600]`，`exam.retry_max = 6`）：

```
第 1 次失败 → 1s 后再试
第 2 次 → 5s
第 3 次 → 30s
第 4 次 → 120s
第 5 次 → 600s
第 6 次 → 3600s
第 7 次失败 → STATUS_DEAD（累计约 72 分钟）
```

**结论：不会无限重试**，最迟约 72 分钟后归入死信，之后需人工重放或在配置修好后重放。

## 四、风险登记

### P0-1 `verify_sign=false` 下的服务态伪造

- **触发条件**：平台部署到网关后的 8080，且 `verify_sign` 仍为 `false`
- **攻击路径**：请求自带 `X-Auth-Mode: service`，走分支 2，`peerGuard` 只校验通道能力（`query`/`pull`/`replay` 当前全开），不校验任何凭据
- **可读到什么**：任意 `userId` 的学习进度与准入判定、全量事件增量、死信重放
- **可达范围**：公网需先过网关 L2（有签名保护），但**同机其余四个平台与内网直连 8080 均可**，构成横向移动面
- **检出方式**：`curl -H 'X-Auth-Mode: service' http://<host>:8080/api/v1/learning/internal/peers/forum/students/usr_10000/progress`
- **处置**：上线前必须置 `true`

### P0-2 AppKey 真名未确认

- 报告称网关预置 4 个 AppKey 但未列名，验收脚本只出现 `jy-exam-svc`
- 配置值 `jy-learning-svc` 为按命名规律推测
- 错误表现：`40108 AppKey 未注册`，与 `40105 签名不匹配` 在网关日志中相邻，极易被误判为算法问题而反复排查签名
- **处置**：执行注入前先列出 `secrets.json` 的 `app_keys` 键名

### P1-1 迁移未先执行导致 SQL 错误

新代码的 `findPullable` / `acknowledge` 引用 `acked_at`、`remote_id`、`ack_status`。若代码先于迁移上线，每次拉取与回执都会抛列不存在错误。

- **约束**：迁移必须早于代码，两个迁移文件（`20261105230000`、`20261105233000`）都要跑
- 加列本身向后兼容，旧代码不受影响，因此"迁移先行"没有副作用

### P1-2 注入密钥后出现超时累积

密钥为空时根本不发请求，所以此风险在注入后才生效：

- `CURLOPT_CONNECTTIMEOUT = 2`、`CURLOPT_TIMEOUT = gateway.timeout`（默认 5）
- `flush()` 批量上限 200 条
- 论坛不可达时最坏情况：200 × 2s ≈ 400s，单个 sync 任务被拖至数分钟，后续批次顺延
- **处置**：先确认论坛端点健康（`/api/v1/forum/internal/learning/health`）再注入密钥；或临时把批量调小

### P2-1 死信堆积与日志噪声

配置未齐期间，每名结课学生产生 2 条待发事件（exam 假成功、forum 失败），forum 侧约 72 分钟后进死信，期间每次重试写一条 error 日志。属于可预期噪声，配置修好后需批量重放。

### P2-2 网关路由新增的连带影响

`forum-learning-events` 是独立路由条目，与现有 19 条并列，不改动其他路由。风险集中在写入错误（如误改 `forum-internal`），建路由脚本已做 dry-run 与"缺 `jy-l2-sign` 拒绝创建"保护。

### P3 签名计算开销

每条入站请求多一次 `sha256` + `hmac-sha256`，每条出站多一次同量级计算。微秒级，相对框架启动与 DB 查询可忽略。

## 五、性能影响

| 维度 | 变化 | 量级 |
| --- | --- | --- |
| 入站延迟 | +1 次 HMAC 与 1 次 `hash_equals` | 微秒级 |
| 出站延迟 | +1 次公网往返 | 正常 50~200ms；超时路径见 P1-2 |
| outbox 写入 | 结课事件 ×2 | 低频，可忽略 |
| 网关限流 | 200 QPS/AppKey、60 QPS/IP | 推送速率上限；超限得 429，走退避而非死信 |
| sync 任务时长 | 受出站往返支配 | 论坛健康时可忽略，不可达时见 P1-2 |

需要注意：网关是**按 IP 限 60 QPS**，若本平台与其余四平台共用一个出口 IP，推送突发会与它们争抢该配额，表现为偶发 429 而非业务错误。

## 六、兼容性影响

### 6.1 向前兼容

- `/internal/peers/*` 是**新增别名路由**（9 条），原有 `/peers/*` 路径保留，未接入网关的调用方不受影响
- `exam_outbox` 只加列不删改，旧查询不受影响
- `peers.training` 保持停用，行为不变

### 6.2 向后兼容（回退时）

- 关闭 `peers.forum.enabled` 即停止推送，无需回滚代码
- `verify_sign` 可从 `true` 改回 `false`，但**等同于重新打开 P0-1 缺口**，只应作为紧急降级且必须配合网络层限制

### 6.3 开发环境的影响（容易被忽略）

`verify_sign=true` 后，本地无网关的环境**所有请求都会 401**，本地页面与联调脚本失效。当前 `config.php` 是单份文件、靠手工改，存在"部署时忘记改回来"的风险。

建议改用环境区分：

```php
// config.php
$config['gateway']['verify_sign'] = (bool)getenv('JY_GATEWAY_VERIFY_SIGN');
```

生产在 php-fpm 环境注入 `1`，本地默认不设即 `false`。这样避免同一份配置在两处要求相反的情况下出错。

## 七、上线顺序与依赖约束

顺序不可交换，箭头右侧依赖左侧：

```
① 核实 AppKey 真名
      ↓
② 跑两个迁移（加列 + 建表）
      ↓
③ 部署代码 + 清注解缓存/Volt 缓存
      ↓
④ 注入两把密钥 + 置 verify_sign = true
      ↓
⑤ 网关建 forum-learning-events 路由
      ↓
⑥ 论坛侧起端点（systemctl + 建路由）
      ↓
⑦ 联调：A 组验签名过网关 → B 组验平台侧鉴权 → 真实事件闭环
```

各步违反后的具体后果：

| 若违反 | 后果 |
| --- | --- |
| ③ 早于 ② | 拉取/回执抛列不存在，接口 500 |
| ④ 早于 ⑤ | 出站 40300 未登记路径，进死信 |
| ⑤ 早于 ⑥ | 网关路由指向无人监听端口，502 |
| ⑦ 早于 ④ | 平台侧 `--group platform` 全 401，无法区分是密钥错还是签名错 |

清缓存三件套（注解缓存、Volt 缓存、opcache）必须都做：`GatewaySign` 是新类，注解路由新增 9 条，漏清会表现为"路由 404 但代码明明写了"。另注意 opcache `revalidate_freq=2`，改配置后立即请求会读到旧值。

## 八、回滚方案

| 层级 | 操作 | 影响面 | 耗时 |
| --- | --- | --- | --- |
| 代码 | 未推送，`git reset --hard 38aff79` 即回滚全部 | 本地 | 秒级 |
| 代码（已推送） | 按 commit 逐个 `git revert`，8 个提交可按关注点单独回退 | 局部 | 分钟级 |
| 配置 | `peers.forum.enabled = false` 停推送；`verify_sign` 视情况 | 只影响该通道 | 秒级 |

回滚不涉及存量数据迁移，是本方案相对可控的主要原因。唯一要注意的是：**回滚 `verify_sign=true` 到 `false` 是"降级但开门"**，若该环境已对外，应改为在网关或 Nginx 层加 IP 白名单兜底，而不是直接关校验。
