## 3. 页面 / 服务入口、路由与接口清单

### 3.1 页面入口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/account/forum-login` | 论坛账号登录表单 |
| POST | `/account/forum/login` | 提交；需 `csrf_token` 字段 + 同源 Referer |

生产是**裁剪版**：首页无登录/注册链接，`/account/login`、`/account/register` 均为 404，整个账号模块控制器与视图都被删除。因此新增独立入口，而不是把注册/找回密码一整条链路一并放回线上；现有页面一个都没改。

### 3.2 出站接口（账号确认）

`POST http://8.138.246.181/answer/api/v1/account/verify`

- 请求体 JSON 四字段：`login`、`pass`、`login_type`（`auto`）、`client_id`（`jy-learning-svc`），≤64KB，仅 POST
- 请求头五头：`X-App-Key`、`X-Timestamp`、`X-Nonce`、`X-Sign-Alg: HMAC-SHA256`、`X-Signature`
- canonical 七段：`appKey\nts\nnonce\nMETHOD\npath\ncanonicalQuery\nsha256(body)`；`canonicalQuery` 按 `(key, value)` 字典序排序后重编码，**空格编码为 `+`**（不是 `%20`）
- 响应七字段：`confirmed`、`user_id`、`username`、`display_name`、`role`、`e_mail_masked`、`account_source`（另有 `status`）；成功 200，凭据错误 401/`40104`
- 13 个网关错误码映射见 `AccountVerify::ERRORS`

### 3.3 入站接口（`/api/v1/learning/*`，共 15 条）

`progress/{userId}`、`progress/{userId}/{courseId}`、`completion/{userId}/{courseId}`、`peers`、`peers/{source}/handshake`、`peers/{source}/students/{userId}/progress`、`.../completion/{courseId}`、`peers/{source}/events`(POST)、`events/{eventId}`、`receipts`(POST)、`pull`、`replay`(POST)、`progress/push`(POST)、`sync/{eventId}`。

响应统一 `{code, message, data, requestId}`；写操作必须带 `Idempotency-Key`。握手与能力发现免鉴权（不返回学生数据）。

> **路径差异（已兜底）**：网关侧用 `/api/v1/learning/internal/*`，本平台注解路由注册在 `/api/v1/learning/*`。本平台已在 nginx 入口加 `rewrite` 剥离 `internal` 段，两种路径均可访问；握手与能力发现现在下发的都是 upstream 真实路径，并额外给出 `gatewayRoute` / `upstreamRoute` / `pathRewrite` 三个字段。入站签名 canonical 只含七个头、不含 path，剥离不影响验签。

## 4. 鉴权与权限约束

### 4.1 出站 L2

五头签名、±300s 时间窗、nonce 600s 去重、**路径不得重写**（网关若开 `proxy-rewrite`，签名串对不上会返 `40105` 而非 `40300`，容易被误判成算法错误）。

### 4.2 入站三档（可信度从高到低）

1. **用户态**：`X-User-Id` + 有效内部签名 → 身份即该用户
2. **网关服务态**：`X-Auth-Mode: service` + 有效内部签名 → 无 `X-App-Code`，对端身份由路径 `{source}` 决定，受 `peerGuard` 通道约束
3. **对端直连**：`X-App-Code` + 对端签名/令牌，身份收紧到自己的通道
4. **本机调用**：仅 `verify_sign=false` 的联调环境放行

内部签名七字段顺序固定：`X-User-Id / X-User-Role / X-Client-Id / X-Token-Exp / X-Request-Id / X-Auth-Mode / X-Timestamp`，`\n` 拼接后 HMAC-SHA256。

`verify_sign=true` 是安全底线：`X-Auth-Mode` 是客户端可自填的头，不验签等于任何内网机器都能冒充网关。本轮实测「伪造 service 且无签名」返回 401。

### 4.3 限流与权限

- 网关 200 QPS/AppKey + 60 QPS/IP；本平台 10 次/60s/IP（Redis Lua 原子 `INCR`+`EXPIRE`，避免连接中断留下无 TTL 的 key 造成永久封禁；Redis 故障时放行而非拒登）
- 论坛 `admin` **不提权**（落库仍 `edu_role=1`、`admin_role=0`）；`teacher` → `edu_role=2`
- 首次登录建号写入 `hash(random_bytes(32), salt)`，本地密码登录对这些账号恒失败
- 论坛返回的是掩码邮箱（`a***@jspi.edu.cn`），不写入本地邮箱字段，避免占用用户日后要绑定的真实邮箱
- 失败提示不区分「账号不存在」与「密码错误」（防枚举）

## 5. 异常处理与日志

### 5.1 四层错误处理

1. 参数本地先拦（空账号、密码 8–32 位）
2. curl 连接失败 / 超时分开归类，不混成「网关不可用」
3. **非 JSON 2xx 一律判失败**——网关有 catch-all，未登记路径会回 `200 + HTML 默认页`，不拦就会把「路由没配」误当成「账号已确认」
4. 13 个网关码 → 内部 reason → 3 类用户提示（`invalid_credentials` 让用户重试、`account_unavailable` 联系管理员、其余统一「稍后重试」）

`app_secret` 为空时 `isEnabled()` 返回 false，不发请求、登录页不渲染入口；空密钥直接失败，不降级成无签名请求。

### 5.2 日志点（`gateway` 通道 → `storage/log/gateway-YYYY-MM-DD.log`）

`Forum Login Succeeded` / `Forum Login Rejected` / `Forum Login Throttled` / `Learning Api Auth Rejected` / `Forum Account Verify Failed` / `Forum Account Create Exception` / `Forum Account Bound`。

记录：account、错误键、异常类与位置、path/method/ip、requestId、userId、`trustedError`/`peerError`/`appCode`/`authMode`。

**不记录**：`password`、请求体、`X-Internal-Sign` 原文、任何密钥。签名可被离线复算，密钥进日志等于泄露。日志写入整体包 `try/catch` 吞异常——日志故障不能把 401 变成 500，或把登录成功变成失败。

### 5.3 首次部署修正的两处问题

- **CSRF**：基类 `beforeExecuteRoute` 对非安全请求强制校验 CSRF 与同源 Referer，白名单为空；新增表单原先没有 `csrf_token`，POST 被框架转成 `/error/400` 且 catch 抓不到（异常在控制器之外）。已按项目既有约定补隐藏字段。
- **错误提示**：`LearningController` 此前用 `$peer['error']` 取提示，导致所有签名失败都显示「缺少 X-App-Code」。改为优先取 `$trusted['error']`，现在分别返回「缺少 X-Internal-Sign」「请求签名校验失败」「请求时间戳超出允许窗口」。

> 验收脚本注意：CSRF token 是 `encryptBase64` 输出，**可能含 `+`**。浏览器表单会自动编码，但 curl 必须用 `--data-urlencode`，否则 `+` 被解析成空格，表现为偶发 400。

### 5.4 后续复核追加修正的五处问题

首次验收结束后重新逐条核对生产，发现 5 处此前未被覆盖的错误：

| # | 问题 | 根因 | 修复 |
| --- | --- | --- | --- |
| 1 | 握手接口 `GET /peers/forum/handshake` 返回 **500**（空 body） | 新版 `LearningController.php:422` 调用 `$this->getConfig()`，但该方法属于 `Service` trait，控制器基类（本地与生产都没有）不具备 | 改为 `\Phalcon\Di::getDefault()->getShared('config')->path(...)`；已部署，实测 200 |
| 2 | 握手与 `Peers::describe()` 下发的 16 条入站路径全部带 `internal/`，照抄调用必 404 | 控制器 15 条注解路由注册在 `/api/v1/learning/*`，没有 internal 别名；握手 `$prefix`、`gatewayEntry.route` 又互相矛盾 | 下发统一为 upstream 真实路径；nginx 入口加 rewrite 兜底剥离；握手补 `gatewayRoute`/`upstreamRoute`/`pathRewrite` |
| 3 | 握手上把 `outboundReady` 报成 `true` | `Gateway::isConfigured()` 只判 `mode==='gateway'`，不看 `peers.*.enabled`；而 forum 对端是关闭的 | 改为 `$peer['enabled'] && isConfigured()`，notice 区分「未启用」与「未配地址」 |
| 4 | **经网关的服务态请求读任何用户数据都返回 403** | `beforeExecuteRoute` 把 mode 归一化为 `peer-service`，`assertReadable()` 只认 `service`，随后 userId 空 ≠ userKey → 抛 Forbidden | `assertReadable()` 同时接受 `service` / `peer-service`（两者都已验签、权限等价）；实测从 403 变为 404 业务提示 |
| 5 | 生产 `/www/ctc/config/*.bak.*` 留有含明文 `app_secret` 的配置副本 | 配置补丁写前备份落在应用目录 | nginx 已有 `deny all`（外网实测 403），仍将 3 个备份移入 `/root/backup/` 并 `chmod 600`；数据库备份同样收紧 |

> 第 1、4 项最值得注意：它们不会让 401 系列验收失败——旧脚本把「非 401」一律算通过，所以 500 的接口和 403 的服务态都被判成了绿灯。已把 `verify_inbound_sign.py` 的 `passed` 收紧为「必须真正进入业务层」，并新增 internal 前缀两组用例。
