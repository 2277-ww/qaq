## 1 落地的是哪个方案

按选型结论执行「**A 为主干 + E 的 completion 做准入权威 + C 做每日对账**」，并在此之上把"单一考试平台"抽象成**对端注册表**，为实训/论坛留出同一条链路。

| 方案 | 落地形态 | 状态 |
| --- | --- | --- |
| A 窗口式（后端派生 + 发件箱推送） | `/uc/progress` 窗口 + `kg_exam_outbox` + 投递任务 | 已上线 |
| E 纯拉（回源） | `GET /progress`、`GET /completion` | 已上线，作为准入唯一权威 |
| C 批量对账 | `peer_reconcile` 任务，每日 03:47 | 已上线 |
| B 前端直报 | 不采用（不可作准入依据） | 未实现 |
| D 事件流 | 不采用（单消费方时过度设计） | 未实现 |

**关键改造**：`course.completed` 不再固定发往考试平台，而是按 `target` 扇出给所有已启用对端；新增对端只改配置，不改投递代码。

## 2 核心步骤与实现要点

### 步骤 1：把"对端"抽出来（`App\Services\Learning\Peers`）

一处配置 `$config['peers']`，描述每个对端的启用状态、网关路径、事件白名单、扩展通道、入站白名单。

```
$config['peers']['exam']     = ['enabled'=>true,  'events'=>['course.completed'], ...];
$config['peers']['training'] = ['enabled'=>false, 'events'=>['course.completed'], 'inbound_events'=>['practice.submitted','practice.completed']];
$config['peers']['forum']    = ['enabled'=>false, 'events'=>['course.completed'], 'inbound_events'=>['forum.post.created','forum.reply.created']];
```

**要点**：`Peers::allows($peer, $eventType)` 是唯一的通道裁决点，返回 `official | extension | ''`。任何事件进箱前都过这一关，杜绝"手滑发错类型"。

### 步骤 2：事件入箱带 target 与 channel

`kg_exam_outbox` 增加两列：

| 列 | 取值 | 作用 |
| --- | --- | --- |
| `target` | `exam` / `training` / `forum` | 投递时按它取路径与白名单 |
| `channel` | `official` / `extension` | 事件目录内 vs 本地扩展，隔离依据 |

**要点**：去重口径也必须按对端隔离——`existsFact()`、`findLastProgress()` 都带 `target`，否则考试平台推过的完成事件会挡住实训平台的同一条事件。

### 步骤 3：完成事实扇出，中间态改回源

`Collect::courseCompletedFanout()`：给每个已启用且允许该事件的对端各入箱一条，**各自独立 eventId**，某对端失败不影响其他对端。

`learning.progress.updated` 默认不入箱。理由见接入说明 8.1：跨平台正式通道只允许目录内类型，硬发会让下游按"未知主版本"隔离告警。中间态由对端回源 `GET /progress/{userId}` 获取。

**这是本次修掉的一个真实缺陷**：改造前该事件与 `course.completed` 共用同一路径，属于通道纪律违规。

### 步骤 4：投递按 target 路由（`Gateway::sendEvent`）

路径、`X-App-Code` 全部来自注册表；未启用的对端**跳过而不计失败**，事件留在待发状态，启用后由下一轮定时器自动补发。

### 步骤 5：每日对账兜底（`Reconcile`）

扫 `kg_course_user` 中已完成课程，比对发件箱是否已有该对端的 `course.completed`，缺失则重新入箱。只补缺口、不改学习数据，可重复执行。

### 步骤 6：入站收件箱（对端回传）

`kg_peer_inbox` + `(source, event_id)` 唯一键，先登记后处理，HTTP 请求里只做校验与落库。

## 3 预留接口：职责范围、输入输出、调用方式

### 3.1 职责边界

| 方向 | 谁发起 | 我方职责 | 对端职责 |
| --- | --- | --- | --- |
| 出站（我方 → 对端） | 自学平台 | 组装封套、幂等键、签名、重试与死信、对账补发 | 按契约消费、按 eventId 幂等 |
| 入站（对端 → 我方） | 实训/论坛 | 校验白名单与签名、幂等落库、提供状态查询 | 提供封套、失败重试、用同一 eventId |

**明确不做的事**：我方不替对端做业务判定（如实训成绩是否及格），也不接受对端直接改学习数据；入站事件只登记，落地为学情由后续处理器决定。

### 3.2 出站接口（我方推送，对端接收）

| 项 | 约定 |
| --- | --- |
| 方法/路径 | `POST {gateway.base_uri}{peers.<peer>.push_path}` |
| 请求头 | `Content-Type: application/json`、`X-App-Code: learning`、`Idempotency-Key: <eventId>`、`X-User-Id`/`X-Client-Id`/`X-Request-Id`/`X-Auth-Mode: service`/`X-Timestamp`/`X-Internal-Sign` |
| 请求体 | 事件封套（见 3.4） |
| 期望响应 | 2xx 视为成功；4xx 视为契约错误**不重试**直接死信；5xx/超时按 1s/5s/30s/2min/10min/1h 退避，6 次后死信 |
| 事件类型 | 仅 `course.completed`（v1.0）；中间态不在目录内，不发 |

### 3.3 入站接口（对端回传，我方接收）

#### ① 能力发现

```
GET /api/v1/learning/peers
```

响应（节选）：

```json
{"code":"OK","data":{"peers":[
  {"peer":"training","name":"实训平台","enabled":false,
   "outbound":{"appCode":"learning","path":"","events":[],"extensions":{"enabled":false,"path":""},
               "signature":"X-Internal-Sign: hmac-sha256(secret, canonical)","idempotency":"Idempotency-Key = eventId"},
   "inbound":{"enabled":false,"path":"","events":[]}}
],"catalog":["course.completed"]}}
```

用途：对端接入前自检——我支持哪些事件、走哪个路径、要不要入站开关，不用靠口头约定。

#### ② 回传事件

```
POST /api/v1/learning/peers/{source}/events
source ∈ {training, forum}
```

| 入参 | 必填 | 说明 |
| --- | --- | --- |
| `eventId` | 是 | 全局唯一，≤64 字符，对端生成 |
| `eventType` | 是 | 必须在 `peers.<source>.inbound_events` 白名单内 |
| `eventVersion` | 否 | 默认 `1.0` |
| `actorId` | 否 | 对端用户主键，应为 OIDC `sub`（`usr_xxx`） |
| `data` | 否 | 业务载荷，原样保存 |
| 请求头 | 是 | 网关注入的可信头；服务态调用需 `X-Auth-Mode: service` |

响应：

| 状态码 | code | 含义 |
| --- | --- | --- |
| 202 | `OK` + `status: accepted` | 首次受理，返回 `inboxId` |
| 202 | `OK` + `status: duplicate` | 重复投递，幂等返回同一 `inboxId` |
| 400 | `VALIDATION_ERROR` | 缺事件编号/类型，或封套非 JSON |
| 403 | `PEER_NOT_OPEN` | 该对端未开通入站（`enabled` 或 `inbound` 为 false） |
| 422 | `EVENT_NOT_ALLOWED` | 事件类型不在白名单 |

#### ③ 查询受理状态

```
GET /api/v1/learning/peers/{source}/events/{eventId}
```

返回 `status`（0 已接收 / 1 已处理 / 2 已忽略 / 3 处理失败）、`statusText`、`receivedAt`、`processedAt`；未受理返回 404。

### 3.5 调用示例（实训平台侧）

```bash
# 1. 先自检能力
curl -s https://<gateway>/api/v1/learning/peers

# 2. 回传一条实训完成事件（经网关，携带可信头）
curl -X POST https://<gateway>/api/v1/learning/peers/training/events \
  -H 'Content-Type: application/json' \

  -H 'X-Internal-Sign: <hmac>' \

# 3. 对不上账时查状态
```

### 3.6 考试平台反向接口（本轮预留并已联通）

出站推送只解决"我方发出去了"，剩下的三件事靠下面三个接口闭环。三者共用同一套网关约束与响应封套，开关都在 `$config['peers']['exam']` 里，逐项可关。

| 接口 | 方向 | 方法/路径 | 作用 | 开关 |
| --- | --- | --- | --- | --- |
| 回执 | 考试平台 → 我方 | `POST /api/v1/learning/peers/exam/receipts` | 确认入库，回填对端单号 | `ack` |
| 增量拉取 | 考试平台 → 我方 | `GET /api/v1/learning/peers/exam/pull` | 按游标补漏推 | `pull` |
| 失败重放 | 考试平台 → 我方 | `POST /api/v1/learning/peers/exam/replay` | 对账后重推失败/死信事件 | `replay` |

#### ① 回执 `POST /peers/exam/receipts`

考试平台入库成功后回传，本平台把发件箱记录从「已推送」升级为「已确认」，并写入对端单号。事件类型固定 `exam.progress.ack`，靠 `correlationId` 关联原进度事件。

```json
{
  "eventId": "rcpt_20261105_0001",
  "eventType": "exam.progress.ack",
  "eventVersion": "1.0",
  "occurredAt": "2026-11-05T15:00:23Z",
  "correlationId": "evt_CE26FAD850750B24BF18",
  "actorId": "usr_10000",
  "payload": {
    "eventId": "evt_CE26FAD850750B24BF18",
    "status": "accepted",
    "remoteId": "EXAM-2026-000456",
    "reason": ""
  }
}
```

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `eventId` | 是 | 回执自身编号，作幂等键（同一 `eventId` 重复提交返回 `duplicate`） |
| `eventType` | 是 | 必须为 `exam.progress.ack` |
| `correlationId` | 是 | 被回执的进度事件 `eventId`；缺省时回退取 `payload.eventId` |
| `payload.status` | 是 | `accepted` 保持已推送；`rejected` 退回待重试（60 秒后由投递器重发） |
| `payload.remoteId` | 否 | 对端记录号，最长 64 字符，写入 `kg_exam_outbox.remote_id` 供对账反查 |
| `payload.reason` | 否 | 拒绝原因，写入 `last_error` |

响应 `202`：

```json
{"code":"OK","message":"回执已确认","data":{
  "receiptId":"rcpt_test_0002","targetEventId":"evt_CE26FAD850750B24BF18",
  "ackStatus":"accepted","remoteId":"EXAM-2026-000456",
  "ackedAt":"2026-11-05T15:00:23Z","eventStatus":1}}
```

契约码：`RECEIPT_NOT_OPEN`(403) / `EVENT_NOT_ALLOWED`(422，非 ack 类型) / `TARGET_EVENT_NOT_FOUND`(422，原事件不存在或不属于该对端) / `VALIDATION_ERROR`(400)。

#### ② 增量拉取 `GET /peers/exam/pull`

推送失败重试到死信、或对端长时间离线，都可能漏推。拉取给对端一个主动对齐入口：按游标取增量事件，自己按 `eventId` 幂等入库。

| 参数 | 必填 | 说明 |
| --- | --- | --- |
| `userId` | 是 | 对外 userId（OIDC sub 或 `usr_` 占位） |
| `afterId` | 否 | 游标，取 id 大于该值的事件，默认 0 从头取 |
| `since` | 否 | ISO8601 起始时间，如 `2026-11-05T00:00:00Z`，用于限定回溯窗口 |
| `limit` | 否 | 期望条数，默认与上限取 `pull_limit`（200，最大 500） |

```bash
curl "https://<gateway>/api/v1/learning/peers/exam/pull?userId=usr_10000&afterId=0&limit=50"
```

```json
{"code":"OK","data":{"peer":"exam","userId":"usr_10000","channel":"official",
 "afterId":0,"nextCursor":4,"hasMore":false,"limit":50,"count":2,
 "events":[{"eventId":"evt_2287...","eventType":"course.completed","eventVersion":"1.0",
   "occurredAt":"2026-11-05T10:22:50Z","userId":"usr_10000","courseId":2,"progress":100,
   "deliveryStatus":1,"deliveryText":"已推送","acked":false,"remoteId":"",
   "payload":{"...":"完整事件封套，与推送时一致"}}]}}
```

**游标为什么用 `afterId` 而不是时间戳**：同一秒内可能入箱多条事件，时间戳做游标要么重复读、要么漏读；自增 id 单调递增，天然适合续拉。对端只需保存 `nextCursor`，下次带上即可。

`hasMore=true` 时说明还有下一页，继续用 `nextCursor` 拉；`false` 表示已到底。

契约码：`PULL_NOT_OPEN`(403) / `USER_NOT_FOUND`(400) / `VALIDATION_ERROR`(400)。

#### ③ 失败重放 `POST /peers/exam/replay`

死信不自动重试是刻意的——连续失败通常意味着契约变更或对端故障，盲目重试只会放大故障。但对账修好之后需要明确的重推入口。必须带 `Idempotency-Key`。

两种用法：

```bash
# 指定事件
curl -X POST https://<gateway>/api/v1/learning/peers/exam/replay \
  -H 'Content-Type: application/json' -H 'Idempotency-Key: replay-20261105-01' \
  -d '{"eventIds":["evt_CE26FAD850750B24BF18"]}'

# 按条件（该用户 + 可选课程）批量重放
curl -X POST https://<gateway>/api/v1/learning/peers/exam/replay \
  -H 'Content-Type: application/json' -H 'Idempotency-Key: replay-20261105-02' \
  -d '{"userId":"usr_10000","courseId":1}'
```

```json
{"code":"OK","data":{"peer":"exam","requested":0,"replayed":1,
 "eventIds":["evt_CE26FAD850750B24BF18"],
 "skipped":[],"deliveredBy":"exam_sync（3 分钟一轮）或下一次一键同步"}}
```

跳过原因：

| reason | 含义 |
| --- | --- |
| `NOT_FOUND` | 事件不存在，或不属于该对端 |
| `EVENT_NOT_ALLOWED` | 事件类型不在该对端的事件目录白名单内（如中间态进度） |
| `ALREADY_PENDING` | 已是待投递，无需重放 |
| `ALREADY_SENT` / `ALREADY_ACKED` | 已投递 / 已被对端确认 |

**重放只重置状态、不在请求里直接投递**：投递要出网、耗时不可控，不能占着请求线程；重置后由 `exam_sync`（3 分钟一轮）或下一次一键同步自然接走，两条路径都通。单次上限 100 条。

#### 三条一致性纪律

1. **回执不放开事件目录**：`exam.progress.ack` 只存在于反向通道，不进 `Peers::CATALOG`，避免被当作可出站类型。
2. **拉取只输出目录内事件**：同时校验 `channel=official` 与 `event_type` 命中白名单。只查 `channel` 不够——改造前的存量事件 `channel` 被统一补成了 `official`，中间态会漏给对端。
3. **重放只重放目录内事件**：把不该上正式通道的历史事件重推出去，等于主动制造一次 8.1 违规，所以按 `eventIds` 显式指定时也会校验 `Peers::allows()`。

### 3.7 对端服务态鉴权（`PeerAuth`）与握手

**为什么需要它**：考试平台调我们时手里没有用户令牌，原先只认网关注入的 `X-User-Id`，服务态请求会在网关未配好的阶段全部落到"本地放行"，等于没有鉴权；网关配好后又因为没有用户身份被 `assertReadable` 拒绝。

身份来自对端自己的应用编码，与用户链路完全分开：

| 项 | 用户态（网关） | 服务态（对端） |
| --- | --- | --- |
| 身份来源 | 网关注入 `X-User-Id` + `X-Auth-Mode` | `X-App-Code` + `X-Internal-Sign` |
| 识别字段 | `X-User-Id` | `peers.<对端>.inbound_app_code` |
| 校验 | `TrustedHeader::verify()`，7 段 canonical | `PeerAuth::authenticate()`，4 段 canonical |
| 权限 | 只能读自己的数据 | 只能访问自己那条 `/peers/{自己}/*` 通道 |

签名串（对端可自行实现，无需了解网关的 7 段格式）：

```
canonical = appCode + "\n" + requestId + "\n" + timestamp + "\n" + sha256_hex(rawBody)
signature = lowercase_hex(hmac_sha256(peers.<对端>.secret, canonical))
```

三档鉴权，配置驱动、代码零改动：

| `auth_mode` | 生效条件 | 适用阶段 |
| --- | --- | --- |
| `signature` | `auto` 且有 `secret`，或显式指定 | 上线标准 |
| `token` | `auto` 且有 `token`，或显式指定 | 网关已做统一鉴权 |
| `none` | 两者都没有 | 仅联调；页面会显示「入站仅编码校验」提示待加固 |

判定顺序（`beforeExecuteRoute`）：

1. 网关用户态（有 `X-User-Id` 且校验通过）→ 放行，走原逻辑；
2. 对端服务态（`X-App-Code` 校验通过）→ 放行为 `mode=peer`；
3. 握手/能力发现路径 → 免鉴权放行（不返回任何学生数据）；
4. 未接入网关的本地环境且**未声明** `X-App-Code` → 放行为 `mode=local`；
5. 其余 → 401。

第 4 条是刻意保留的联调后门，但**带了 `X-App-Code` 就必须通过校验**——否则随便填一个编码就能绕过，等于没有鉴权。这一条曾在上线复测时漏掉，被"伪造 `X-App-Code: hack` 仍返回 200"验证出来。

### 3.8 握手与查询接口（考试平台侧）

| 接口 | 鉴权 | 说明 |
| --- | --- | --- |
| `GET /peers/{source}/handshake` | 免 | 契约版本、鉴权档位、签名串形式、能力开关、事件封套示例、`outboundReady` |
| `GET /peers/{source}/students/{userId}/progress` | 服务态 | 学习进度快照（需 `query=true`） |
| `GET /peers/{source}/students/{userId}/completion/{courseId}` | 服务态 | 准入判定（需 `query=true`） |

握手是给对端的**自检入口**，用来回答三个问题，避免双方靠猜联调：我的 `X-App-Code` 配对了吗（`appCodeMatched`）；该签什么串（`auth.signature.canonical`）；哪条能力还没对我开（`capabilities.*.enabled`）。`outboundReady=false` 时明确告知"我方尚未配置你的网关地址，事件只入箱不外发"，而不是让对方在收不到数据时怀疑自己。

对端能力检查统一收敛到 `peerGuard()`：

```php
peerGuard($source, $ability)
  ├─ 未登记      → 404 PEER_NOT_FOUND
  ├─ 身份是别的对端 → 403 PEER_SCOPE_DENIED
  └─ 能力未开通   → 403 <ABILITY>_NOT_OPEN
```

`assertReadable()` 额外拒绝 `mode=peer`：服务态身份不能走用户态接口 `/progress/{userId}`，必须走 `/peers/{自己}/students/...`，保证两条链路的权限边界清晰。

### 3.9 出站鉴权（我们对端）

| 配置 | 作用 |
| --- | --- |
| `peers.<对端>.access_token` | 该对端网关要求的 Bearer 令牌，覆盖 `gateway.access_token` |
| `peers.<对端>.headers` | 附加请求头，适配 APISIX key-auth（`X-API-Key`）等插件 |

令牌按对端取而不是全局共用：五平台各自的网关鉴权相互独立，考试平台的 token 不能拿去调论坛平台的网关。头名在注册表里做了 `^[A-Za-z0-9-]+$` 校验，防止配置写错把头注入带进请求。

## 4 需遵循的网关约束

| # | 约束 | 出处 | 实现对应 |
| --- | --- | --- | --- |
| 1 | 跨平台写操作**必须经网关**，不得直连对端 | 接入说明总则 | 所有外发只走 `Gateway`，无对端直连代码 |
| 2 | 入站只信网关注入头，且校验 `X-Internal-Sign` | 5.2 / 5.3 | `TrustedHeader::verify()`，canonical 顺序固定 7 段 |
| 3 | 时间戳偏移超过 `timestamp_skew`（默认 300s）拒绝 | 5.2 | 超窗返回 `timestamp_expired` → 401 |
| 4 | 写操作必须带 `Idempotency-Key`，按 eventId 去重 | 5.2 / 6.3 | `progress/push` 缺键返回 400；投递头固定 `Idempotency-Key = eventId` |
| 5 | 跨平台通道只发**事件目录内**类型 | 8.1 | `Peers::allows()` 白名单，`learning.progress.updated` 默认不发 |
| 6 | 本地扩展事件必须与正式通道隔离 | 8.1 | `channel=extension` + 独立 `extension_path`（默认关闭） |
| 7 | 高频上报允许 5s 节流 | 6.3 第 7 项 | 进度事件按 5 个百分点节流；中间态改为回源，不占通道 |
| 8 | 4xx 不重试，5xx 退避重试 | 8.4 | 4xx → 死信；退避 1/5/30/120/600/3600s，6 次转死信 |
| 9 | 响应统一 `{code,message,data,requestId}` | 6.5 | `sendEnvelope()` 统一封装，`X-Request-Id` 回显 |
| 10 | 一个对端故障不得影响其他对端 | — | 按 target 独立入箱与投递；未启用对端跳过不计数 |

## 5 后续对接实训平台时的扩展点

按"要改什么、改哪里、注意什么"列，前三条不改代码。

| # | 扩展点 | 怎么改 | 注意 |
| --- | --- | --- | --- |
| E1 | 出站事件类型 | 改 `peers.training.events` 数组 | 训练类事件（如 `practice.completed`）不在接入说明 8.1 目录内，**必须走 extension_path**，不能直接加进 `events` |
| E2 | 入站白名单 | 改 `peers.training.inbound_events` + `inbound=true` | 白名单先小后大；放开一个类型前先确认消费逻辑能处理，否则只登记不消费会积压 |

| E5 | 身份映射 | 确认实训侧 `actorId` 就是 OIDC `sub`；否则先建绑定表 | 映射不到必须返回 404，**不可兜底成默认用户**——否则数据串号 |
| E6 | 入站事件消费 | 新增消费者读 `kg_peer_inbox` 中 `status=0` 的记录，处理完置 1/3 | 当前只登记不消费，这是**遗留 TODO**；处理必须幂等，按 `(source,eventId)` 再去一次重 |
| E7 | 乱序与重复 | 消费侧按 `occurredAt` 判新旧、按业务主键取 max | 网络重试会产生重复投递，登记幂等只保证不重复入库，不保证业务顺序 |
| E8 | 对账范围 | `Reconcile` 目前只对 `course.completed`；实训事件需扩展 | 对账要覆盖"我方发出去的"和"对端回传的"两个方向，别只对一半 |
| E9 | 监控 | 加 `kg_peer_inbox` 积压与 `dead` 数量告警 | 死信只记日志，没有告警通道，长时间堆积不会被发现 |
| E10 | 路径落定 | `peers.training.push_path` 现为占位 `/api/v1/training/learning/progress` | 必须由实训平台给正式路径后再启用，否则会 4xx 直接死信 |
| E11 | 复用反向接口 | 实训/论坛要回执、拉取、重放时，把 `peers.<对端>.ack/pull/replay` 置 true 即可，**代码零改动** | 回执事件类型仍限定 `exam.progress.ack`；若对端要用别的回执名，改 `Receipt::EVENT_ACK` 与 `inbound_events` 两处，别只改一处 |
| E12 | 对端单号语义 | `remote_id` 目前默认按考试平台成绩单编号理解 | 实训/论坛的 `remoteId` 可能是任务号、帖子号，长度已限 64 字符；语义差异写进对端对接文档，别指望同一个字段表达所有含义 |

**两个联调坑（值得记住）**：

1. `php-fpm` 的 `opcache.revalidate_freq=2`，改完 `config.php` 立即请求仍走旧配置，自检会出现"配了密钥却没校验"的假阴性。自检脚本已加 3 秒等待，手工验证时也要留出这个窗口。
2. 握手免鉴权不能用 `dispatcher` 的 action 名判断——action 取值受 camelize / 后缀 / 命名风格配置影响，一旦变化握手就被 401 挡掉，对端反而拿不到签名规范。改为按请求路径匹配后稳定。
