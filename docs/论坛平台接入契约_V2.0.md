## 1 一句话说明

学习平台在**学生课程结课**时，经统一网关向论坛推送一条 `course.completed` 事件；论坛可以反过来查学生学习进度、拉取漏推的事件、回传帖子/回复事件。

两个方向都必须经过网关，且**签名是两套**——这是最容易出错的地方，第 3 章专门讲。

## 2 网络与路径

```
┌──────────────┐   L2 签名    ┌────────────────────┐   重算内部签名   ┌──────────────┐
│  学习平台     │ ───────────> │  APISIX 网关        │ ───────────────> │  论坛 9088    │
│  (8080)      │              │  8.138.246.181:80   │                  │  或接收端点   │
└──────────────┘              └────────────────────┘                  └──────────────┘
        ^                              │
        └──────────────────────────────┘
              论坛回调走同一条网关
```

### 2.1 学习平台 → 论坛（推送）

| 项 | 值 |
| --- | --- |
| 地址 | `POST http://8.138.246.181/api/v1/forum/internal/learning/progress` |
| 网关路由 | `forum-learning-events`（需网关侧新增，见第 6 章） |
| 上游 | `127.0.0.1:9082`（论坛侧接收端点） |
| 必须头 | `X-App-Key` / `X-Timestamp` / `X-Nonce` / `X-Sign-Alg` / `X-Signature` / `Idempotency-Key` |

> **为什么是 `/internal/`**：网关对 `/api/v1/forum/*` 走 L1 会话鉴权，服务态调用没有用户令牌，会被 40101 拒掉。`/api/v1/forum/internal/*` 才是 L2 机器调用档，并且有独立的 200 QPS/AppKey 配额，不与论坛前台 60 QPS/IP 抢桶。

### 2.2 论坛 → 学习平台（查询 / 拉取 / 回执）

| 用途 | 路径 |
| --- | --- |
| 对接握手（拿契约、签名规范、能力清单） | `GET /api/v1/learning/internal/peers/forum/handshake` |
| 查学生学习进度 | `GET /api/v1/learning/internal/peers/forum/students/{userId}/progress` |
| 查课程完成状态（准入判定） | `GET /api/v1/learning/internal/peers/forum/students/{userId}/completion/{courseId}` |
| 增量拉取事件（补漏推） | `GET /api/v1/learning/internal/peers/forum/pull?afterId=0&limit=200` |
| 请求重放失败事件 | `POST /api/v1/learning/internal/peers/forum/replay` |
| 回传论坛事件 | `POST /api/v1/learning/internal/peers/forum/events` |

前缀 `/api/v1/learning/internal/` 对应网关的 `learning-internal` 路由（L2 + 200 QPS/AppKey）。**不要用 `/api/v1/learning/peers/...`**，那条会被 L1 拦成 40101。

## 3 鉴权：两套签名，别混

网关转发时会做两件事，顺序不能颠倒：

1. **验 L2 签名**（论坛提供 `X-App-Key` + `X-Signature`）→ 不通过直接 40105，请求到不了学习平台
2. **剥离入站身份头，重算 `X-Internal-Sign` 注入上游** → 学习平台验这一把

所以：

| 方向 | 论坛要做什么 | 学习平台要做什么 |
| --- | --- | --- |
| 论坛 → 学习平台 | 签 L2（第 3.1） | 验网关重算的内部签名 |
| 学习平台 → 论坛 | 不用做 | 签 L2 + 网关重算内部签名 |
| 论坛接收推送 | 验内部签名（第 3.2） | —— |

### 3.1 L2 签名（过网关用）

```
canonical = appKey        \n
            timestamp     \n
            nonce         \n
            METHOD        \n      ← 大写
            path          \n      ← 仅路径，不含域名与 query
            canonicalQuery \n     ← 无 query 时是空串
            sha256(rawBody)       ← 十六进制小写；空体是 sha256("") 而不是空串

X-Signature = hex( HMAC-SHA256( appSecret, canonical ) )
```

请求头：

| 头 | 说明 |
| --- | --- |
| `X-App-Key` | 论坛的应用标识，由网关发放 |
| `X-Timestamp` | 秒级，允许 ±300 s |
| `X-Nonce` | 每次唯一，网关按 (AppKey, nonce) 去重 600 s |
| `X-Sign-Alg` | 固定 `HMAC-SHA256` |
| `X-Signature` | 上面的 hex 结果 |

**canonicalQuery 的两个坑**（都踩过）：

- 排序键是 `(key, value)` 而不是只按 key。同名参数 `a=2&a=1` 只按 key 排会顺序不定。
- 空格编码成 `+` 而不是 `%20`。网关基准实现是 Python `urlencode`（quote_plus 语义），PHP 的 `rawurlencode` 给出 `%20`，两者签名长度相同、极难察觉。

Python 参考实现：

```python
import hashlib, hmac, time, uuid, urllib.parse

def l2_headers(app_key, app_secret, method, path, body=b""):
    ts, nonce = str(int(time.time())), uuid.uuid4().hex
    p = urllib.parse.urlsplit(path)
    q = urllib.parse.parse_qsl(p.query, keep_blank_values=True)
    q.sort(key=lambda kv: (kv[0], kv[1]))
    canonical = "\n".join([
        app_key, ts, nonce, method.upper(), p.path,
        urllib.parse.urlencode(q), hashlib.sha256(body).hexdigest(),
    ])
    return {
        "X-App-Key": app_key,
        "X-Timestamp": ts,
        "X-Nonce": nonce,
        "X-Sign-Alg": "HMAC-SHA256",
        "X-Signature": hmac.new(app_secret.encode(), canonical.encode(),
                                hashlib.sha256).hexdigest(),
    }
```

### 3.2 网关注入的内部签名（论坛接收推送时验）

网关转发前重算并注入七个身份头 + `X-Internal-Sign`：

```
canonical = X-User-Id \n X-User-Role \n X-Client-Id \n X-Token-Exp
          \n X-Request-Id \n X-Auth-Mode \n X-Timestamp

X-Internal-Sign = hex( HMAC-SHA256( internalSignKey, canonical ) )
```

- 服务态调用时 `X-User-Id`、`X-User-Role`、`X-Token-Exp` 通常为空串
- `X-Auth-Mode` 为 `service`
- 密钥是「网关 ↔ 论坛」这一对，**与学习平台那把不同**，各自向网关侧索取

> 字段顺序以网关 `jy-identity.lua` 为准。本契约与学习平台实现均按上述顺序；若网关侧不同，只改拼接顺序，算法不变。

### 3.3 网关错误码

| 码 | 含义 | 处理 |
| --- | --- | --- |
| 40105 | 签名缺失或不匹配 | 检查 canonical 拼接，重点看 query 排序与空格编码 |
| 40106 | 时间戳超出 ±300 s | 校时（chronyd / ntp） |
| 40107 | nonce 重放 | 每次请求重新生成，不要复用 |
| 40108 | AppKey 未注册 | 找网关方确认 AppKey |
| 40101 | 走了 L1 路由 | 换 `/internal/` 前缀 |
| 40300 | 路径未登记 | 路由没配或前缀写错 |

## 4 事件契约

### 4.1 封套

```json
{
  "eventId": "evt_0123456789ABCDEF",
  "eventType": "course.completed",
  "eventVersion": "1.0",
  "occurredAt": "2026-11-05T10:00:00Z",
  "sourcePlatform": "learning",
  "sourceEntityId": "course_2",
  "actorId": "usr_10000",
  "correlationId": "",
  "requestId": "req_0123456789ABCDEF",
  "data": {
    "userId": "usr_10000",
    "courseId": "course_2",
    "progress": 100,
    "completed": true
  }
}
```

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `eventId` | 是 | 幂等键，同一事件重试时保持不变 |
| `eventType` | 是 | 当前仅 `course.completed` 可上正式通道 |
| `eventVersion` | 是 | 主版本变化表示不兼容 |
| `occurredAt` | 是 | UTC ISO8601 |
| `data.userId` | 是 | 对外用户主键（`usr_` 前缀） |
| `data.courseId` | 是 | 课程标识 |
| `data.progress` | 是 | 0–100 |
| `data.completed` | 是 | 是否结课 |

### 4.2 幂等

学习平台的投递器按指数退避重试（1s / 5s / 30s / 2min / 10min / 1h），同一 `eventId` 会到达多次。

**重复投递必须返回 200**，不要返回 409 或 4xx——那会让对方一直重试到进死信。建议响应体：

```json
{"code":"OK","message":"该事件已入库，幂等返回","data":{"received":true,"duplicate":true,"eventId":"evt_..."}}
```

### 4.3 论坛回传事件

论坛 → 学习平台，走 `POST /api/v1/learning/internal/peers/forum/events`：

| eventType | 触发 | 建议 data |
| --- | --- | --- |
| `forum.post.created` | 学生发帖 | `userId`, `postId`, `boardId`, `createdAt` |
| `forum.reply.created` | 学生回帖 | `userId`, `replyId`, `postId`, `accepted` |

同样要求幂等，`eventId` 唯一。学习平台侧按 `(source, eventId)` 去重。

## 5 论坛需要实现的东西

只有一个接收端点：

| 项 | 值 |
| --- | --- |
| 路径 | `POST /api/v1/forum/internal/learning/progress` |
| 监听 | `127.0.0.1:9082`（不对公网开放） |
| 验签 | 第 3.2 节的内部签名 |
| 幂等 | 按 `eventId` 去重，重复返回 200 |
| 白名单 | 只收 `course.completed`，其余返回 422 |
| 响应 | `{"code":"OK","message":"...","data":{"received":true,"duplicate":false}}` |

**论坛本体（9088）不需要改。** 接收端点独立起进程，网关加一条更长的前缀路由分流即可。

参考实现、systemd 单元与部署步骤见 `deploy/learning-progress/forum_endpoint/`。

### 5.1 为什么不用论坛现有接口

论坛现有 API 都在 `/answer/api/v1/*`，且信任自己的会话体系、不验内部签名。直接把学习平台的请求转过去，等于让一条无鉴权的路径能写论坛数据。单独起端点是更小的改动面。

## 6 网关侧需要做的两件事

### 6.1 新增一条路由

```python
{
  "id": "forum-learning-events",
  "uri": "/api/v1/forum/internal/learning/*",
  "upstream": {"type": "roundrobin", "nodes": {"127.0.0.1:9082": 1}},
  "plugins": { ... }   # 必须包含 jy-l2-sign + jy-identity + jy-gw-error
}
```

**必须复制 `forum-internal` 的插件配置**，不能手写：漏掉 `jy-l2-sign` 就等于让接收端点公网裸奔。`deploy/learning-progress/forum_endpoint/add_forum_learning_route.py` 会自动从 Admin API 读出 `forum-internal` 的配置、只替换 uri 与 upstream 后写回，并在缺少 `jy-l2-sign` 时拒绝创建。

APISIX 按最长前缀匹配，`/api/v1/forum/internal/learning/*` 优先于 `/api/v1/forum/internal/*`，论坛自己的内部 API 不受影响。

### 6.2 可选：把 AppKey 转发给上游

当前网关只验 AppKey，不把它透传给上游。后果是上游无法区分「这次服务态调用是哪家平台发起的」，只能靠路径里的 `{source}` 认通道。

如果希望服务态调用被钉回自己的通道，给 `learning-internal` 与 `forum-*` 路由加一个头注入即可（不改路径，仍满足「路径不重写」约束）：

```json
"proxy-rewrite": {
  "headers": { "set": { "X-App-Key": "$http_x_app_key" } }
}
```

学习平台侧已经实现了对应校验：请求里带 `X-App-Key` 时，会与该通道登记的对端 AppKey 比对，不一致返回 `403 PEER_SCOPE_DENIED`。所以网关补上这条，学习平台不用改代码就会自动收紧。
