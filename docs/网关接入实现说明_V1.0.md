## 一、接入目标与协议

### 1.1 两条链路，别混在一起

本平台与统一网关之间是**双向**关系，两条链路的鉴权方式、失败语义、部署依赖都不同：

| 链路 | 方向 | 用途 | 鉴权 | 当前状态 |
| --- | --- | --- | --- | --- |
| **出站** | 本平台 → 网关 → 论坛 | 论坛账号确认 | L2 服务签名（五头） | 代码就绪，缺 AppSecret |
| **入站** | 网关 → 本平台 | 学习进度/对端事件 | L1 用户态 / L2 服务态 / 对端签名 | 代码就绪，缺网关 upstream |

账号确认**只依赖出站**。入站是另一条线，不影响账号确认能否跑通——这一点决定了排障顺序：先通出站，再看入站。

### 1.2 协议约定

| 项 | 值 |
| --- | --- |
| 传输 | HTTP/1.1（出站明文；入站 HTTPS） |
| 方法 | **仅 POST**，其他方法网关返 `400/40001` |
| Content-Type | `application/json; charset=utf-8` |
| 编码 | UTF-8，不做二次转义（签名按原始字节哈希） |
| 体积 | ≤ 64 KB（超出返 `413/41300`） |
| 超时 | 网关侧 3 s（S 级）；本平台侧 5 s |
| 重定向 | 禁止跟随（跟随会改变 path，签名立即失效） |

### 1.3 地址

```
出站网关      http://8.138.246.181
出站路径      /answer/api/v1/account/verify
入站本平台    https://8.138.34.151        （nginx → /www/ctc/public）
入站前缀      /api/v1/learning/*
```

## 二、路由与转发规则

### 2.1 出站：账号确认

```
本平台 BFF
  └─ POST http://8.138.246.181/answer/api/v1/account/verify
       ├─ jy-l2-sign    验 AppKey / 时间窗 / nonce / 报文摘要
       ├─ jy-identity   剥离伪造的 X-User-* 头，注入七头 + X-Internal-Sign
       └─ 转发 127.0.0.1:9088，**路径不重写**
            └─ 论坛只读查询 user / registered_account / user_role_rel，bcrypt 比对
```

**路径不重写**是关键约束：网关把 `/answer/api/v1/account/verify` 原样交给论坛 9088，
本平台签名时用的 path 必须与之逐字一致。一旦网关侧开启 `proxy-rewrite`，
签名串对不上，表现为 `40105` 而非 `40300`，极易误判为算法错误。

平台侧需要做的只有三件事：生成五头、发 POST、读 `data.confirmed`。网关路由与论坛端点无需改动。

### 2.2 入站：网关 → 本平台（需网关方配置）

本平台**不监听 8080**——实测 `8.138.34.151` 只有两个入口：

| 端口 | nginx server | 根目录 / 用途 |
| --- | --- | --- |
| 443 | `ctc-ssl.conf`，`server_name _` | `/www/ctc/public`，本平台 |
| 80 | `plaza.conf`，`server_name 8.138.34.151` | 广场（Halo） |

因此网关 upstream 的**最终目标**应是 **`https://8.138.34.151:443`**（Let's Encrypt IP 证书，公信链，APISIX 无需跳过校验）。

> ⚠️ **表 7 修正了本文初版的一处误判**：网关报告里的 `8080` 不是模板笔误，它是**网关机 `8.138.246.181` 本机回环** `127.0.0.1:8080`（`routes.py` 153–161 行），三平台分别 learning 8080 / exam 8090 / workshop 8000。与本平台 `8.138.34.151` 没有 8080 并不矛盾：网关把请求先转给本机 8080 的桩/反代，再由那一跳转给本平台 443。**需要网关方做的是把 8080 回环桩替换为反代到 443**，而不是直接改 APISIX upstream 节点。实测该桩：`GET /api/v1/learning/auth/login` 返回 `{"platform":"learning","sign_valid":true,...}`；8080/8090/8000/9088 公网均不可达。

期望的网关侧配置（**由网关方执行，本平台不改网关**）：

```yaml
# APISIX：本平台 upstream
upstreams:
  - id: learning-api
    type: roundrobin
    scheme: https
    nodes:
      "8.138.34.151:443": 1
    timeout:
      connect: 2
      send: 3
      read: 5

# 路由：服务态（机器调用，L2）
routes:
  - id: learning-internal
    uri: /api/v1/learning/internal/*
    methods: [GET, POST]
    upstream_id: learning-api
    priority: 2600
    plugins:
      jy-l2-sign:
        app_keys: [jy-learning-svc, jy-exam-svc, jy-workshop-svc, jy-plaza-svc]
      jy-identity:
        inject: [X-User-Id, X-User-Role, X-Client-Id, X-Token-Exp,
                 X-Request-Id, X-Auth-Mode, X-Timestamp]
        sign: X-Internal-Sign
      limit-count:
        count: 200
        time_window: 1
        key_type: var
        key: http_x_app_key
```

上游超时 `read: 5` 与平台侧 `gateway.timeout = 5` 对齐，避免网关先断开、
平台把「上游慢」误报成「网关不可达」。

**若网关方只能走 80 明文**：80 端口当前被 `plaza.conf`（广场）占用，
需要在该 server 块内加一条前缀分流，把学习接口转给本平台：

```nginx
# /etc/nginx/conf.d/plaza.conf，放在现有 location 之前
location ^~ /api/v1/learning/ {
    proxy_pass https://127.0.0.1:443;
    proxy_http_version 1.1;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto https;
    proxy_read_timeout 10s;
}
```

注意 `X-Forwarded-For` 只用于日志，**不参与鉴权**：入站身份一律取网关注入的
`X-User-Id` 与 `X-Internal-Sign`，不能信任任何客户端可伪造的转发头。

### 2.3 入站路径规划

| 方法 | 路径 | 语义 | 鉴权档 |
| --- | --- | --- | --- |
| POST | `/api/v1/learning/internal/peers/{source}/events` | 接收对端回传事件 | 服务态 |
| GET | `/api/v1/learning/internal/peers/{source}/events/{eventId}` | 查询受理状态 | 服务态 |
| POST | `/api/v1/learning/internal/peers/{source}/receipts` | 接收投递回执 | 服务态 |
| GET | `/api/v1/learning/internal/peers/{source}/pull` | 按游标增量拉取 | 服务态 |
| POST | `/api/v1/learning/internal/peers/{source}/replay` | 失败事件重放（需 `Idempotency-Key`） | 服务态 |
| GET | `/api/v1/learning/internal/peers/{source}/handshake` | 对接握手，返回契约版本与鉴权要求 | **免鉴权** |
| GET | `/api/v1/learning/internal/peers/{source}/students/{userId}/progress` | 查学习进度 | 服务态 |

握手免鉴权是刻意的：对端接入前拿不到密钥，只能先读契约；该端点不返回任何学生数据。

## 三、鉴权与限流约束

### 3.1 出站 L2 签名（本平台实现）

规范化串七段，以 `\n` 连接，段内不得含换行：

```
appKey \n timestamp \n nonce \n METHOD \n path \n canonicalQuery \n sha256Hex(rawBody)
```

请求头五件：

| 头 | 约束 |
| --- | --- |
| `X-App-Key` | `jy-learning-svc`，须在网关与论坛两侧白名单 |
| `X-Timestamp` | Unix 秒，偏差 ≤ ±300 s |
| `X-Nonce` | 每次唯一，网关 600 s 内去重 |
| `X-Sign-Alg` | 固定 `HMAC-SHA256` |
| `X-Signature` | 小写十六进制 HMAC-SHA256 |

实现：`app/Services/Learning/GatewaySign.php`（`headers()` / `sign()` / `canonical()`）。

**两个已踩过的坑**，代码里已固化：

- `canonicalQuery` 的空格必须编码成 `+` 而非 `%20`（网关基准用 Python `urlencode`）；
  两者长度相同、肉眼难辨，错了只会得到 `40105`。
- 排序键是 `(key, value)` 而不只是 key。只按 key 排时，`a=2&a=1` 这类同名参数顺序不定。

### 3.2 入站三档鉴权

`app/Http/Api/Controllers/LearningController::beforeExecuteRoute` 按优先级依次尝试：

| 顺序 | 档位 | 判据 | 身份来源 |
| --- | --- | --- | --- |
| 1 | 用户态（L1） | `X-Auth-Mode` 缺失或 `user`，且 `X-User-Id` 非空 | 网关注入的 `X-User-Id` |
| 2 | 网关服务态（L2） | `X-Auth-Mode: service` | URL 中的 `{source}`，受通道能力约束 |
| 3 | 对端直连 | 自带 `X-App-Code` + `X-Request-Id` + `X-Timestamp` + `X-Internal-Sign` | `X-App-Code` 认到的具体对端 |
| 4 | 本机调用 | 未接网关的复现环境，`verify_sign=false` | 无身份，仅限联调 |

**注意第 2 档的安全性前提**：`X-Auth-Mode: service` 本身是可伪造的头，
之所以能作为依据，是因为走到这一步说明 `TrustedHeader` 已按 `gateway.verify_sign`
校验过 `X-Internal-Sign`。**生产环境 `verify_sign` 必须为 `true`**，
否则内网任何机器都能直连服务、自带一个 `X-Auth-Mode: service` 冒充网关。
这也是当前 `config.php` 里 `verify_sign = false` 不能上线的直接原因。

内部签名七字段，顺序固定：

```
X-User-Id \n X-User-Role \n X-Client-Id \n X-Token-Exp \n
X-Request-Id \n X-Auth-Mode \n X-Timestamp
```

实现：`app/Services/Learning/TrustedHeader.php` + `Gateway::sign()`。

### 3.3 限流（三层）

| 层 | 维度 | 阈值 | 实现位置 |
| --- | --- | --- | --- |
| 网关 | AppKey | 200 QPS | 网关 `limit-count` |
| 网关 | 源 IP | 60 QPS | 网关全局桶 |
| 本平台 | 客户端 IP | 10 次 / 60 s | `app/Services/Gateway/LoginThrottle.php` |

本平台这一层不是重复建设：账号确认把用户密码转发出去，本平台因此成了论坛账号确认的
**代理入口**。不限流，任何人都能借这个入口对论坛做密码尝试——论坛侧虽有防枚举，
但代价是消耗配额、写满审计日志，而本平台毫无感知。

计数与过期用 Lua 原子执行（`INCR` + `EXPIRE` 不可分两步）：若中间连接断开，
key 会永久留存，等于把这个 IP 永久封禁。

**Redis 故障时放行**，只记 `Login Throttle Unavailable` 警告。登录是主路径，
缓存不可用不应让所有用户都登不进来——此时失去的是防刷能力，而不是可用性。

## 四、配置方式

### 4.1 配置文件键（`config/config.php`）

```php
// 出站：账号确认
$config['gateway']['account_base']    = 'http://8.138.246.181';
$config['gateway']['account_path']    = '/answer/api/v1/account/verify';
$config['gateway']['account_timeout'] = 5;   // 网关预算 3s + 网络余量
$config['gateway']['account_login_limit']  = 10;
$config['gateway']['account_login_window'] = 60;

// L2 凭据（出站）
$config['gateway']['app_key']    = 'jy-learning-svc';
$config['gateway']['app_secret'] = '07e7…9fd4';  // 已注入（64 位 hex），不入库

// 入站
$config['gateway']['internal_sign_secret'] = '';  // ← secrets.json → internal.learning.secret（第 9 行）
$config['gateway']['verify_sign']      = false;   // 生产必须 true
$config['gateway']['timestamp_skew']   = 300;
```

`app_secret` 与 `internal_sign_secret` 是**两把不同的密钥，不能互换**：

- `app_secret` 过网关 L2（验完即剥离，不进上游）
- `internal_sign_secret` 供本平台校验网关重算后注入的内部签名

任一为空时，指向网关的请求**直接失败并记录原因**，不会降级成无签名请求——
降级会造成「看起来在发、其实全被拒」或更糟的「被网关当匿名放行」。

### 4.2 密钥注入（不进命令行历史）

`deploy/learning-progress/apply_forum_peer.sh`：

```bash
# 在**网关机**上执行，从 secrets.json 直接读，密钥不落 shell history
ssh root@8.138.246.181
cd /path/to/deploy && ./apply_forum_peer.sh \
    --config /www/ctc/config/config.php \
    --secrets /etc/jingyuan-gateway/secrets.json --dry-run   # 先看
```

脚本行为：只替换 `$config['gateway']['app_secret'] = '...';` 这一行的字面量，
保留其余内容与注释；写前备份，写后 `php -l`，语法不过自动回滚。

**注意**：脚本默认读 `/etc/jingyuan-gateway/secrets.json`，该文件只存在于网关机。
本平台机上没有这个目录（实测 `NO_GATEWAY_DIR`），直接在 8.138.34.151 上跑会报
「读不到密钥文件」。两种正确做法：在网关机上执行；或先把值取出来再手工写入。

### 4.3 生效

```bash
redis-cli -n 3 eval "local ks=redis.call('keys','_PHCR_ANNOTATION_:*'); for i,k in ipairs(ks) do redis.call('del',k) end; return #ks" 0
rm -f /www/ctc/storage/cache/volt/*.php

sleep 3   # opcache 有约 2s 延迟，改完立刻请求会读到旧配置
```

## 五、调用示例

### 5.1 业务侧：一行调用

```php
use App\Services\Logic\Account\ForumLogin;

// 控制器/服务层，校验与建号都在内部完成，失败抛业务异常
$user = (new ForumLogin())->handle($login, $password, 'auto');
```

真正接入点在 `app/Http/Home/Services/Account::loginByForum()`：先按 IP 限流，
再交给 `ForumLogin`。限流维度取 IP 而非账号名——账号名可被任意枚举，
按账号计数挡不住「换一个账号继续试」。

### 5.2 直接调用网关（curl）

```bash
BODY='{"login":"admin@jspi.edu.cn","pass":"Admin@12345","login_type":"auto","client_id":"jy-learning-svc"}'
TS=$(date +%s); NONCE=$(openssl rand -hex 16)
CANON="jy-learning-svc
$TS
$NONCE
POST
/answer/api/v1/account/verify

$(printf %s "$BODY" | sha256sum | cut -d' ' -f1)"
SIG=$(printf %s "$CANON" | openssl dgst -sha256 -hmac "$APP_SECRET" -hex | awk '{print $NF}')

curl -sS --noproxy '*' -X POST http://8.138.246.181/answer/api/v1/account/verify \
  -H 'Content-Type: application/json' \
  -H "X-App-Key: jy-learning-svc" -H "X-Timestamp: $TS" -H "X-Nonce: $NONCE" \
  -H 'X-Sign-Alg: HMAC-SHA256' -H "X-Signature: $SIG" \
  -d "$BODY"
```

注意 `canonicalQuery` 段为空时**留空行但保留换行**——上面 `CANON` 里 POST 与 sha256 之间那一行是空行。

### 5.3 Python（与论坛方示例对齐）

```python

status, resp = verify_account("admin@jspi.edu.cn", "Admin@12345", "jy-learning-svc")
if status == 200 and resp["data"]["confirmed"] is True:
    ...  # 建立本平台会话
```

### 5.4 成功响应

```json
{"code":200,"message":"ok","data":{
  "confirmed":true,"user_id":"1","username":"admin","display_name":"admin",
  "role":"admin","e_mail_masked":"a***@jspi.edu.cn","account_source":"legacy",
```

## 七、错误处理与日志

### 7.1 错误分层

```
参数层   本地先拦（login 1–100 字符、pass 8–32、body ≤ 64KB）  → 不打网关
传输层   curl errno：超时 / 连接失败                          → 分别归类
协议层   非 JSON 响应                                          → 判失败，不判成功
业务层   网关数字码 13 个                                       → 映射为内部 reason
用户层   只暴露 3 类提示，其余统一「稍后重试」
```

**协议层那条不能省**：网关有 catch-all 路由，未登记的路径会回 `200 + HTML 默认页`。
不校验响应体就会把「路由没配」当成「账号已确认」，这是最危险的一种假成功。

### 7.2 错误码 → 处理方式

| 码 | 含义 | 平台处理 | 对用户提示 |
| --- | --- | --- | --- |
| `40104` + `invalid_credentials` | 账号或密码错 | 不重试 | **账号或密码错误**（唯一该提示用户的） |
| `40104` + `account_unavailable` | 账号停用/删除 | 不重试 | 账号不可用，联系管理员 |
| `40001` | 参数非法 | 不重试 | 请检查输入 |
| `40105` | 签名不符 | 告警，人工介入 | 稍后重试 |
| `40106` | 时间戳超窗 | 校时告警 | 稍后重试 |
| `40107` | nonce 重放 | 每次请求重新生成 | 稍后重试 |
| `40108` | AppKey 未注册/停用 | 告警 | 稍后重试 |
| `40300` | 路由未登记 | 告警（配置错误） | 稍后重试 |
| `40303` | 绕过网关 / 伪造内部签名 | **安全告警** | 稍后重试 |
| `42901` | 限流 | 按 `Retry-After` 退避 | 稍后重试 |
| `41300` | 体积超限 | 不重试 | 稍后重试 |
| `50200` / `50400` | 上游不可达 / 超时 | 可重试 | 稍后重试 |
| `50000` | 论坛内部错误 | 带 `requestId` 反馈运维 | 稍后重试 |

设计取舍：账号不存在与密码错误**故意返回同一结论**。若本平台再细分，
两个平台各泄露一点信息，拼起来就是账号枚举工具。

### 7.3 日志点

| 位置 | 级别 | 内容 | 不含 |
| --- | --- | --- | --- |
| `Account::loginByForum` 限流命中 | warning | IP、retryAfter | 账号密码 |
| `ForumLogin::reject` | warning | login、status、reason、错误详情、requestId | **password** |
| `ForumLogin::resolve` 契约异常 | error | username、requestId | — |
| `ForumLogin::create` 建号异常 | error | forumUid、异常消息 | — |
| `ForumLogin::fillProfile` 绑定成功 | info | userId、forumUid、role、accountSource | 邮箱、手机 |
| `LoginThrottle` Redis 故障 | warning | 异常消息 | — |
| `LearningController::logReject` | warning | requestId、path、method、IP、trustedError、peerError、appCode、authMode | **X-Internal-Sign、密钥** |

**日志里绝不能出现密码**。论坛侧审计只记 `login` 不记 `pass`；本平台若在这里
把密码打出来，等于在整条链路上开了一个明文旁路，而且是留存更久的那一个。

同样，**`X-Internal-Sign` 与任何密钥不进日志**：签名可被离线复算，
密钥一旦进日志就等于泄露，而日志的留存与访问面远大于配置文件。

`logReject` 内部整体 `try/catch` 吞掉异常：日志失败不能改变鉴权结论，
否则一个日志故障会把 401 变成 500。
