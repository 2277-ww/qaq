## 2 逐条纠正

### 2.1 「catch-all 路由把未配置路径回成 200，属于异常」

**原判断**：`/*` → 9088 是一条兜底路由，把「没配上」伪装成成功，建议删除。

**实际情况**：`forum-root` 路由 `/*` → `127.0.0.1:9088` 是**刻意的设计**——论坛是网关后唯一的真实业务系统，全站页面（`/`、`/questions`、`/users/login`）都靠这条路由对外。删掉它，论坛前台直接不可用。

**为什么会误判**：探测时 `/random_nonexist_123` 返回了 APISIX 默认页而不是论坛的 404 页。这是**论坛上游对未知路径的处理**，不是网关多了一条兜底路由。真正的兜底在论坛应用里。

**正确做法**：保留 `forum-root`。防假成功那一侧已经由 `Gateway::isAcceptableResponse()` 解决——HTML 响应一律判失败，不依赖网关侧是否清理路由。

### 2.2 「补三条路由（含 `/api/v1/learning/*` 反向）」

**原判断**：网关缺路由，需要补三条。

**实际情况**：网关已注册 **19 条路由**，覆盖全部五个平台，且 `learning-api`、`learning-internal`、`learning-auth` 三条都已存在并验收通过。

**为什么会误判**：探测用的路径是 `/api/v1/forum/learning/progress`，这条**本来就不该存在**——网关的论坛服务态路径是 `/api/v1/forum/internal/*`。路径选错，命中了 `/*`，于是看起来像「路由没配」。

**正确做法**：不改网关路由（除新增一条论坛学习事件路由）。本平台的入站接口前缀改为 `/api/v1/learning/internal/peers/*`，正好落进已存在的 `learning-internal` 路由。

### 2.3 「去掉 jwt-auth，改 proxy-rewrite 注入可信头」

**原判断**：网关用 jwt-auth，服务态调用带不了 JWT，建议换成 proxy-rewrite。

**实际情况**：网关**根本没有用 jwt-auth**。它用四个自研插件：

| 插件 | 优先级 | 职责 |
| --- | --- | --- |
| `jy-identity` | 1030 | 剥离八个入站可信头 → 注入七头 + `X-Internal-Sign` |
| `jy-l2-sign` | 1013 | 服务态 HMAC 签名（我们需要的正是这一档） |
| `jy-l1-token` | 1012 | 用户令牌自省 |
| `jy-gw-error` | 1 | 网关错误页转 JSON |

`jy-identity` 做的就是「剥离 + 注入可信头」，正是原方案想用 proxy-rewrite 达到的效果，而且做得更完整（含防伪剥离）。

**正确做法**：什么都不用改。服务态调用走 L2 路由即可。

### 2.4 「按平台设置独立限流配额」

**原判断**：需要补独立配额。

**实际情况**：已经有。`learning-internal`、`exam-internal`、`workshop-internal` 各 200 QPS/AppKey，`plaza-internal` 100 QPS/接口，论坛前台 60 QPS/IP。抢桶问题不存在。

### 2.5 「`/api/v1/learning/*` 强制 Bearer 鉴权，服务态调用会被 40101 拒」

**原判断**：正确，但结论不完整。

**实际情况**：`learning-api`（`/api/v1/learning/*`）确实是 L1 会话鉴权，服务态调用会 40101。但网关**同时**提供了 `learning-internal`（`/api/v1/learning/internal/*`）走 L2。

**实测证据**（2026-11-05，公网）：

```
GET /api/v1/learning/peers/forum/handshake
→ 401 {"code":40101,"message":"缺少访问令牌"}

GET /api/v1/learning/internal/peers/forum/handshake
→ 401 {"code":40105,"message":"服务签名头不全，需 X-App-Key / X-Timestamp / X-Nonce / X-Signature"}
```

第二条正好确认了 L2 要求的四个头，与本次实现的 `GatewaySign` 完全对应。

**正确做法**：入站路径用 `/internal/` 前缀，网关零改动。

## 4 验证记录

### 4.1 签名一致性（本地 PHP ↔ 网关 Python 基准）

用 `verify_gateway.py` 的 `l2_headers()` 作为基准，构造 8 个用例与 PHP 实现交叉比对：

| 用例 | 覆盖点 | 结果 |
| --- | --- | --- |
| no-query | 无 query 时为空串而非 `?` | 一致 |
| with-query | query 排序 | 一致 |
| get-empty | 空体 `sha256("")` | 一致 |
| dup-keys | 同名参数按 (key,value) 排序 | 一致 |
| space-value | 空格编码 `+` | 一致 |
| cn-value | 中文参数百分号编码 | 一致 |
| blank-value | `flag=` 空值保留 | 一致 |
| unicode-body | UTF-8 请求体摘要 | 一致 |

**8/8 一致**。这是整条链路最关键的验证——签名差一个字节就全盘 40105。

### 4.2 论坛接收端点（本地）

8 个用例全通过：无签名 401、错签名 401、时间戳超窗 401、正确签名 200 新增、
重复投递 200 duplicate、非白名单事件 422、缺 `eventId` 400、篡改参与签名的头 401。

### 4.3 公网网关

已确认 `/api/v1/learning/internal/peers/forum/handshake` 走 L2（返回 40105）。
完整 A 组用例需要 `APP_SECRET`，待密钥注入后执行。

## 5 遗留与风险

| # | 项 | 影响 | 处置 |
| --- | --- | --- | --- |
| 1 | 网关不透传 AppKey 给上游 | 服务态调用只能靠路径认通道，一家对端理论上可读另一家的通道 | 已实现前向兼容校验；网关补 `proxy-rewrite` 头注入后自动收紧（见契约 6.2） |
| 2 | 论坛侧验签字段顺序未核实 | 若 `jy-identity.lua` 顺序与本实现不同，论坛端点会全量 401 | 部署后先用一个用例核对；只需改 `SIGN_FIELDS` 一个列表 |
| 3 | 两把密钥未注入 | 出站会以 `gateway_app_secret_missing` 失败（不是静默降级） | 跑 `apply_forum_peer.sh` |
| 4 | 网关路由 `forum-learning-events` 未建 | 推送会命中 `forum-root`，被论坛当未知路径 | 跑 `add_forum_learning_route.py` |

| 6 | 论坛回传事件无消费者 | 数据入库但不产生业务价值 | 另写学情汇总任务 |
