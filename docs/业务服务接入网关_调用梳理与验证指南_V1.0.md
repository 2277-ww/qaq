## 2. 当前服务的调用方式与依赖关系

### 2.1 出站（本平台 → 网关 → 对端）

```
┌─ A. 学习进度投递 ─────────────────────────────────────────────┐
│ Collect::progressUpdated（业务埋点）                            │
│   → kg_exam_outbox 发件箱（状态0 待发）                         │
│   → ExamSyncTask 定时器 → Sync::flush()（退避重试调度）          │
│   → Gateway::sendEvent($peer, ...)                             │
│       ├─ Peers 注册表：push_path / 通道白名单 / base_uri 回退    │
│       ├─ GatewaySign：L2 五头（X-App-Key…X-Signature）          │
│       └─ Gateway::buildSignHeaders：X-Internal-Sign 七字段头     │
│   → curl POST http://8.138.246.181{push_path}                  │
│ 对端：exam → /api/v1/exam/internal/learning/progress            │
│       training(workshop) → /api/v1/workshop/internal/...        │
│       forum → /api/v1/forum/internal/...                        │
└────────────────────────────────────────────────────────────────┘
┌─ B. 论坛账号确认（登录）───────────────────────────────────────┐
│ ForumLoginController → LoginThrottle(10次/分/IP)                │
│   → AccountVerify → POST {gateway.account_base}/answer/api/v1/ │
│     account/verify（仅 L2 五头）→ 本地建号/绑定 kg_account       │
└────────────────────────────────────────────────────────────────┘
┌─ C. 能力发现 ──────────────────────────────────────────────────┐
│ GET /api/v1/learning/peers：下发对端真实路径、事件类型、签名规范  │
└────────────────────────────────────────────────────────────────┘
```

### 2.2 入站（网关 → 本平台）

```
网关 learning-internal 路由（L2 验签后转发）
  → https://8.138.34.151:443（Let's Encrypt IP 证书）
  → nginx location ^~ /api/v1/learning/internal/ → rewrite 剥离 internal 段
  → LearningController（三档判定：anonymous / service / peer-service）
      ├─ TrustedHeader：X-Internal-Sign 七头 HMAC 验签
      │   （verify_sign=true，密钥 internal_sign_keys["learning"]）
      ├─ 失败 → logReject（AppLogger gateway 通道，可审计）
      └─ 通过 → assertReadable / peerHandshakeAction / 事件入库
```

## 3. 已完成的配置、路由与请求转发调整

### 3.1 配置（生产 `/www/ctc/config/config.php` 已生效）

| 配置项 | 目标值 | 说明 |
|---|---|---|
| `gateway.base_uri` | `http://8.138.246.181` | 网关入口；留空=本地直连模式（只入箱不外发） |
| `gateway.app_key / app_secret` | `jy-learning-svc` / 64hex | L2 五头凭据，对端可在 peers 段覆盖 |
| `gateway.internal_sign_secret` | 64hex（learning 专属那把） | 入站七头验签密钥，**与论坛侧那把不是同一把** |
| `gateway.verify_sign` | `true` | 入站必须验 X-Internal-Sign，防内网冒充 |
| `gateway.timeout` | `5`（连接 2s 硬编码） | 超过即按失败进入退避重试 |
| `gateway.expect_json` | `true` | 2xx 但返回 HTML（catch-all 默认页）判失败，防假成功 |
| `exam.push_path` | `/api/v1/exam/internal/learning/progress` | **必须带 internal 段**：不带会落 L1 档回 40101 |
| `peers.training.push_path` | `/api/v1/workshop/internal/learning/progress` | 实训平台在网关叫 **workshop**；`/api/v1/training/*` 是 40300 未登记 |
| `peers.forum` | `app_key=jy-learning-svc`，push_path 指向 `/api/v1/forum/internal/...` | 等网关建路由后按实际路径再对齐（I8） |
| `gateway.account_base / account_path` | `http://8.138.246.181` + `/answer/api/v1/account/verify` | 论坛账号确认独立配置，不与投递共用空值语义 |

### 3.2 路由与转发逻辑

- **出站**：`Peers` 注册表驱动，新增对端只改配置不改代码；`baseUri()` 对端级为空时
  回退全局 `gateway.base_uri`，不会出现「单对端假成功」。
- **入站 nginx**：`location ^~ /api/v1/learning/internal/` 入口 rewrite 剥离 `internal` 段，
  网关剥与不剥都兼容；`nginx -t` 通过并已 reload。
- **请求头**：L2 五头与内部签名七字段头在同一请求并存；两者都含 `X-Timestamp`，
  经网关时只由 L2 头携带（实测重复头会被网关判 40106）。

## 4. 常见接入问题的处理方式（本方实现，均已实测）

| 问题 | 处理 | 实测证据 |
|---|---|---|
| **认证鉴权** | 双规范并存：网关 L2 五头（入口鉴权，验完即剥离）+ X-Internal-Sign 七字段头（网关重算注入上游，本平台入站验签）。`verify_sign=true` 后伪造头一律 403 | plaza-internal 签名验证 `sign_valid:true`；入站 8 组用例 ALL PASS（含伪造头剥离） |
| **超时** | curl 连接 2s、总超时 `gateway.timeout`=5s；论坛登录另有 `account_timeout`=5s | 网关拒绝即时返回；超时按网络层失败处理（code=0） |
| **重试** | 发件箱模式：失败按 **1s/5s/30s/2min/10min/1h** 退避，`exam.retry_max`=6 次后转死信；**408/429 视为可重试**（限流/超时是瞬态），其余 4xx 契约错误直接死信不空耗重试 | probe 事件 401 → retry_count=1 → status=3（死信），一次往返不空转 |
| **错误码透传** | 网关数字码（40101/40105/40106/40107/40108/40300）翻译为可读原因写入 `outbox.last_error`，原始 HTTP 码存 `response_code`，运维一眼可分级 | `last_error = gateway_40108:网关 AppKey 未注册或已停用` |
| **防假成功** | `expect_json=true`：2xx 但响应是 HTML（APISIX catch-all 默认页）判为「未投进」，按可重试失败处理 | forum 路由未建期间投递不会被误标成功 |
| **限流** | 论坛登录 10 次/分/IP（LoginThrottle 固定窗口），与网关 /oauth/* 口径一致；超限回 429 + retryAfter | 验收脚本第 7 组用例覆盖 |
| **幂等** | 每事件带 `Idempotency-Key`（=event_id）与 `X-Request-Id`；网关/对端可安全去重，重试不产生重复副作用 | 发件箱重放安全 |
| **死信恢复** | `ExamSyncTask` 提供重放（replay）：死信重置 retry_count=0 重新入队。**网关放行后必须重放**，否则白名单期间的死信永久丢失 | ExamSyncTask::replay 已实现 |

### 5.2 判定口径速查（网关 L2 错误码模型，实测确立）

| 现象 | 网关返回 | 定位 |
|---|---|---|
| 签名头缺失/不全 | 40105「服务签名头不全」 | 本方没带 L2 头（检查 Gateway.php 版本） |
| 白名单内但签名错 | 40105「服务签名校验失败」 | canonical 七段或密钥不匹配（逐段比对） |
| AppKey 不在路由组白名单 | 40108「AppKey 不存在或已停用」 | **网关侧白名单**，本方代码无关 |
| 重复 X-Timestamp 头 | 40106「时间戳格式非法」 | 本方重复发同名头（已修） |
| 时间窗超限 | 40106 | 时钟漂移 >±300s |
| nonce 重放 | 40107 | 重放旧请求 |
| 路由未登记 | 40300 / 200+HTML | 网关路由缺失或 catch-all |
| L1 档拦截 | 40101「要求访问令牌」 | path 缺 `internal` 段 |

## 6. 注意事项

1. **三把密钥不可混用**：`gateway.app_secret`（L2 出站）、`internal_sign_secret`
   （入站验签，learning 专属）、论坛侧 `gateway-account.json` 那把——互验必失败。
2. **push_path 必须带 `internal` 段**（出站）；入站相反，本平台真实路径**不带** internal，
   由网关或本方 nginx 剥离。两套路径出现在不同配置位置，改的时候看清方向。
3. **网关放行后第一件事是重放死信**：白名单期间所有 exam 推送按契约错误进了死信，
   不重放即永久丢失（`ExamSyncTask::replay`）。
4. **时钟同步**：网关 L2 时间窗 ±300s，两台机器都依赖 NTP；迁移/重启后先查时钟再排障。
5. **`X-Timestamp` 只能发一次**：任何新代码往请求里加头时注意与 L2 五头去重。
6. **nonce 用宽随机源**：`random_bytes(16)`；网关按 (appKey, nonce) 去重 600s。
7. **不要用 2xx 判定投递成功**：catch-all 路由会回 200 + HTML；业务层以
   `expect_json` + 对端业务响应为准。
8. **探针脚本带密钥走 STDIN**，不落盘、不入库；用完即删探针数据
   （probe_outbox_flush 已自动清理）。
9. **Admin API（9180）只能在网关机本机调用**，公网不可达——我方无法代网关方
   核对路由配置，只能从外部行为推断（§1 即是）。
10. **对端实现进度**：exam 未实现接收端点（404 契约未定义）、workshop 上游是回显桩
    ——即使白名单放行，这两条推送也需对端先交付实现。
