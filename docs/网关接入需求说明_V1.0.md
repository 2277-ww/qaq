## 二、网关类型与协议

| 项 | 需求 / 现状 |
| --- | --- |
| 网关类型 | Apache APISIX 3.13（自研插件 `jy-l2-sign`、`jy-identity`，非 jwt-auth） |
| 出站地址 | `http://8.138.246.181` |
| 入站上游 | `https://8.138.34.151:443`（本平台 nginx，Let's Encrypt IP 证书） |
| 应用层协议 | HTTP/1.1 + `application/json; charset=utf-8` |
| 方法 | **仅 POST**；其他方法返回 `400/40001` |
| 请求体积 | ≤ 64 KB（超出 `413/41300`） |
| 编码 | UTF-8，不做二次转义；签名按原始字节哈希 |
| 重定向 | **不跟随**。跟随会改变 path，签名立即失效 |
| 幂等 | 账号确认只读，天然幂等；重试安全 |

**为什么要求「仅 POST」**：账号确认的请求体含明文密码。GET 会把密码写进
URL、access log、浏览器历史与代理日志。这条约束不是风格偏好，是安全边界。

| 项 | 值 |
| --- | --- |
| 网关路径 | `POST /answer/api/v1/account/verify` |

## 四、鉴权规则

### 4.1 出站：L2 服务签名（本平台自行生成）

请求头五件，缺一即 `40105`：

| 头 | 约束 |
| --- | --- |
| `X-App-Key` | `jy-learning-svc`，须在网关 `routes.py` 的 `l2([...])` 与论坛 `allowed_app_keys` 两处白名单内 |
| `X-Timestamp` | Unix 秒，偏差 ≤ ±300 s |
| `X-Nonce` | 每次唯一，600 s 内去重 |
| `X-Sign-Alg` | 固定 `HMAC-SHA256` |
| `X-Signature` | 小写 hex，`HMAC-SHA256(appSecret, canonical)` |

规范化串七段，`\n` 连接，段内不得含换行：

```
appKey \n timestamp \n nonce \n METHOD \n path \n canonicalQuery \n sha256Hex(rawBody)
```

**两个必须双方一致的细节**（本平台已按网关基准实现，实测通过）：

1. `canonicalQuery` 中空格编码为 `+`（Python `urlencode` 语义），不是 `%20`。
   两者签名长度相同、肉眼难辨，错了只会得到 `40105`。
2. 排序键是 `(key, value)` 而非仅 key。只按 key 排时 `a=2&a=1` 顺序不定。

### 4.2 入站：网关向下游注入的可信头

网关验签通过后，需注入并按固定顺序签名：

```
X-User-Id \n X-User-Role \n X-Client-Id \n X-Token-Exp \n
X-Request-Id \n X-Auth-Mode \n X-Timestamp
```

结果放在 `X-Internal-Sign`。**注入前必须剥离客户端自带的同名头**——
否则客户端可以自己构造 `X-User-Id`，网关再把它原样转发，等于没有身份。

`X-Auth-Mode` 取值 `user`（L1 用户态）或 `service`（L2 服务态）。

### 4.3 需要网关方提供的一把密钥

| 用途 | 键名 | 现状 |
| --- | --- | --- |
| 出站过网关 | `app_keys["jy-learning-svc"].secret` | 已提供，已实测通过 |
| 入站验网关注入签名 | `internal_sign_keys["learning"]` | **未提供** |

截图给出的 `76b309d9…102f1` 是**论坛侧** `gateway-account.json` 的
`internal_sign_secret`（网关 → 论坛那一跳），与本平台要的
`internal_sign_keys["learning"]` 不是同一个值，不能代用。

在拿到之前，本平台 `gateway.verify_sign` 保持 `false`，入站不启用验签。

## 五、路由规则

### 5.1 出站（现状，无需改动）

```
POST /answer/api/v1/account/verify
  ├─ jy-l2-sign    验 AppKey / 时间窗 / nonce / 报文摘要
  ├─ jy-identity   剥离伪造可信头，注入七头 + X-Internal-Sign
  └─ proxy 127.0.0.1:9088，**路径不重写**
```

**路径不得重写**：本平台签名时用的 path 必须与网关转发给论坛的 path 逐字相同。
一旦开启 `proxy-rewrite`，签名串对不上，表现为 `40105` 而非 `40300`，
排查时会误判成算法错误。

### 5.2 入站（需配置）

```yaml
upstreams:
  - id: learning-api
    type: roundrobin
    scheme: https
    nodes:
      "8.138.34.151:443": 1
    timeout:
      connect: 2
      send: 3
      read: 5

routes:
  - id: learning-internal
    uri: /api/v1/learning/internal/*
    methods: [GET, POST]
    upstream_id: learning-api
    priority: 2600
    plugins:
      jy-l2-sign:
        app_keys: [jy-learning-svc, jy-exam-svc, jy-workshop-svc, jy-plaza-svc]
      jy-identity:
        inject: [X-User-Id, X-User-Role, X-Client-Id, X-Token-Exp,
                 X-Request-Id, X-Auth-Mode, X-Timestamp]
      limit-count:
        count: 200
        time_window: 1
        key_type: var
        key: http_x_app_key
```

若网关方只能走 80 明文，本平台在 `plaza.conf` 加前缀分流即可，不需网关改协议：

```nginx
location ^~ /api/v1/learning/ {
    proxy_pass https://127.0.0.1:443;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto https;
}
```

## 六、期望的转发行为

| 行为 | 期望 | 理由 |
| --- | --- | --- |
| 路径 | 原样转发，不改写、不加前缀 | 路径参与签名 |
| 请求体 | 字节级原样转发，不重新序列化 | 签名对 body 取 SHA-256 |
| `Content-Type` | 保留 `application/json` | 论坛按此解析 |
| 可信头 | 先剥离客户端同名头，再注入 | 防伪造身份 |
| 超时 | 出站 3 s；入站 `read: 5` s | 与平台侧 5 s 对齐，避免网关先断开 |
| 重试 | 幂等请求可重试；**不要自动重试 `POST` 写操作** | 无 `Idempotency-Key` 时会重复受理 |
| 压缩 | 不强求；若开启需保持 `Content-Encoding` 与 body 一致 | 解压后再哈希会验签失败 |
| `X-Request-Id` | 全链路透传，响应头与 `data.request_id` 一致 | 跨系统排障的唯一关联键 |
| 缓存 | `Cache-Control: no-store` | 响应含身份信息 |

**关于自动重试**：网关若对 `5xx` 自动重放请求，写类接口需要本平台按
`Idempotency-Key` 去重。账号确认是只读的，重放无副作用，不在此列。

## 七、期望的错误处理行为

### 7.1 响应包络

成功与失败都用同一层信封，HTTP 状态码与 `code` 字段并存：

```json
{"code":40104,"message":"账号确认失败",
 "data":{"confirmed":false,"reason":"invalid_credentials","request_id":"6c9fca52-…"}}
```

**要求 `code` 与 HTTP 状态码保持一致**。平台侧先看 HTTP 状态，再用 `code` 细分；
两者矛盾时以 `code` 为准，并将矛盾记入日志（属于网关契约异常）。

### 7.2 失败语义

| 码 | 含义 | 平台处理 | 是否重试 |
| --- | --- | --- | --- |
| `40104` + `invalid_credentials` | 账号或密码错 | 提示「账号或密码错误」 | 否 |
| `40104` + `account_unavailable` | 账号停用/删除 | 提示联系管理员 | 否 |
| `40001` | 参数非法 | 提示检查输入 | 否 |
| `40105` | 签名不符 | 告警，人工介入 | 否（原样重试必然再失败） |
| `40106` | 时间戳超窗 | 校时告警 | 校时后重试 |
| `40107` | nonce 重放 | 重新生成 nonce | 是 |
| `40108` | AppKey 未注册/停用 | 告警 | 否 |
| `40300` | 路由未登记 | 告警（配置错误） | 否 |
| `40303` | 绕过网关 / 伪造内部签名 | **安全告警** | 否 |
| `42901` | 限流 | 按 `Retry-After` 退避 | 是 |
| `41300` | 体积超限 | 压缩请求体 | 否 |
| `50200` / `50400` | 上游不可达 / 超时 | 稍后重试 | 是 |
| `50000` | 论坛内部错误 | 带 `requestId` 反馈运维 | 是 |

### 7.3 两条硬性要求

**一、失败不得伪装成成功。** 网关存在 catch-all 路由，未登记路径会返回
`200 + HTML 默认页`。平台侧已按「非 JSON 响应一律判失败」处理，
但也请网关方在新增平台路由时避免让未知路径落到论坛默认页——
两者同时兜底，才不会出现「路由没配却被记成账号已确认」。

**二、`40104` 的两种 reason 必须区分。** `invalid_credentials` 是用户输入问题，
`account_unavailable` 是账号状态问题，处置路径完全不同（前者让用户重试，
后者要联系管理员）。合并成一个码会让所有停用账号的用户反复试密码。

### 7.4 日志要求

| 侧 | 记录 | 禁止记录 |
| --- | --- | --- |
| 网关 | AppKey、client_id、结论、reason、requestId、耗时 | 密码、`X-Signature` 原文、密钥 |
| 论坛 | `[account-verify]` 前缀，AppKey、login、login_type、结论、requestId | 密码、bcrypt 摘要 |
| 本平台 | login、status、reason、requestId、IP（限流） | 密码、`X-Internal-Sign`、密钥 |

密码在任何一层的日志里出现，都等于在整条链路上开了明文旁路，
且日志的留存与访问面远大于配置文件。

## 九、验收标准

按顺序执行，任一步失败即停，不往后走。

| # | 动作 | 期望 |
| --- | --- | --- |
| 1 | 错误密码请求账号确认 | `401` + `40104` + `invalid_credentials`（证明签名通过） |
| 2 | 正确凭据请求 | `200` + `confirmed: true` + `user_id` 非空 |
| 3 | 篡改 `X-Signature` | `401` + `40105` |
| 4 | 重放同一 nonce | 首次 `200`，第二次 `401` + `40107` |
| 5 | 时间戳回拨 1 小时 | `401` + `40106` |
| 6 | 未知 AppKey | `401` + `40108` |
| 7 | 同一请求体 70 KB | `413` + `41300` |
| 8 | 直连 9088 伪造 `X-Internal-Sign` | `403` + `40303` |
| 9 | 本平台登录页出现「论坛账号」标签 | 用论坛账号登录成功，`kg_account.forum_uid` 有值 |
| 10 | 入站：`GET /api/v1/learning/internal/peers/forum/handshake` | 返回 JSON 契约，非论坛 HTML |

第 1–8 项在第 0 节已经用真实网关跑过第 1、2 项；第 3–8 项此前已在本地
独立验签网关上 9/9 通过，可在部署后对公网复跑。
