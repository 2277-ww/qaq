# 1 选型说明

## 1.1 目的与范围

本报告是《自学平台软件需求规格说明书 V1.0》的配套技术调研，目的是为自学平台的工程实现寻找可参考、可借鉴的开源实现，回答三个问题：

1. 现成的开源在线学习系统，能在多大程度上覆盖本平台的需求？
2. 若以某个开源项目为参考基线，哪些能力可以直接借鉴，哪些必须自研？
3. 各项目在界面组织、进度模型、权限治理上的做法，哪些值得本平台采用？

需要说明的是，本报告讨论的是**参考价值**，不是采购决策。自学平台是独立工程，需与论坛 SSO、实训工坊、考试平台、成长档案联动，并受《五平台前端与功能联动约束规范 V1.0》约束，因此不存在“直接部署一个开源系统即完成交付”的路径。本报告的落点是：以开源项目为参照物，校准本平台的设计判断，降低从零设计带来的返工风险。

## 1.2 筛选方法与硬性门槛

候选项目来自三条线索：中文开源社区的在线教育/企业培训系统、国际主流开源 LMS、以及技术社区高讨论度的现代课程平台。全部候选先过四道硬门槛，任一不满足即排除：

| 门槛 | 要求 | 排除理由示例 |
|---|---|---|
| G1 许可 | 开源许可明确，允许私有化部署与二次开发 | 仅提供商业授权或源码不开放者排除 |
| G2 可验证 | 存在可公开访问的在线演示，或可在本机低成本跑通 | 演示站长期不可达、无法验证界面者排除 |
| G3 范围相关 | 至少覆盖“课程—课时—学习进度”三段核心链路中的两段 | 纯考试系统、纯直播工具排除 |
| G4 边界可裁剪 | 超出本平台边界的功能（考试、支付、社区）可以关闭而不影响主链路 | 强耦合无法裁剪者排除 |

通过硬门槛的项目，再按 1.3 的维度打分。打分只用于排序与说明差异，不构成采购评分。

## 1.3 评估维度

| 维度 | 权重 | 观察点 |
|---|---|---|
| 课程与分类模型 | 20% | 是否支持多级分类、章节—课时两层结构、图文与视频两类课时 |
| 内容生产与发布 | 15% | 教师侧编排体验、发布前后的状态管理、是否具备审核环节 |
| 学习进度采集 | 20% | 是否记录课时级进度、是否有覆盖率/完成度概念、是否可汇总到课程 |
| 学习工具 | 10% | 收藏、笔记、我的学习等学生侧工具 |
| 角色与治理 | 10% | 学生/教师/管理员三角色划分是否清晰，权限粒度 |
| 对外能力 | 10% | 是否提供开放接口或事件，能否支撑跨平台取数 |
| 技术栈契合 | 10% | 前端是否 React 系、能否与 Ant Design 5 体系复用交互范式 |
| 二次开发成本 | 5% | 代码结构、文档、中文支持、部署复杂度 |

## 1.4 候选池与取舍结果

| 项目 | 类型 | 结论 | 说明 |
|---|---|---|---|
| PlayEdu | 企业培训系统（Java + React） | 入选 | 演示站稳定，学员端与管理端均可访问；课程分类、课时进度、必修/选修划分与本平台高度同构 |
| 酷瓜云课堂 | 网校/知识付费（PHP Phalcon） | 入选 | 演示站稳定；同时具备点播与图文两类课时，支持微信 H5/小程序形态，贴合本平台微信生态前提 |
| Moodle | 通用 LMS（PHP） | 入选 | 官方示范站点提供学生/教师/管理员多角色账号，进度跟踪与活动完成模型最完整，可作为能力上限参照 |
| MeEdu | 在线教育点播（PHP） | 排除 | 演示域名无法解析，无法验证界面，不满足 G2 |
| LearnHouse | 现代 LMS（Next.js + FastAPI） | 排除 | 演示站 CSS 与媒体资源加载异常，页面结构错位，截图不具备参考价值，不满足 G2 |
| ClassroomIO | 协作式 LMS（Next.js） | 排除 | 演示地址连接超时，不满足 G2 |
| Open edX | 大规模开放在线课程 | 排除 | 体量与部署复杂度远超本项目，且以测验/证书为核心，与本平台“轻学习”定位偏离，不满足 G4 |
| 学之思考试系统 | 考试系统 | 排除 | 核心为组卷判卷，恰属本平台明确排除的范围，不满足 G3 |

最终入选三个项目，分别代表三种典型实现路径：**国内企业培训型**（PlayEdu）、**国内网校型**（酷瓜云课堂）、**国际通用型**（Moodle）。三者互补，覆盖了本平台需要判断的主要设计岔路。

# 2 项目一：PlayEdu

## 2.1 项目概览

| 项目 | 内容 |
|---|---|
| 项目名称 | PlayEdu 企业培训系统（开源版） |
| 代码仓库 | https://github.com/PlayEdu/PlayEdu（Gitee 同步：playeduxyz/playedu） |
| 开源许可 | Apache-2.0 |
| 技术栈 | 后端 Java + Spring Boot 3 + MySQL；前端 React 18，前后端分离；提供 PC 端、H5 端、管理后台三个前端与独立 API 服务 |
| 部署形态 | Docker Compose 一键部署，默认开放 9900（后台）/9800（PC）/9801（H5）/9700（API）四个端口 |
| 演示环境 | 学员端 demo.playedu.xyz；管理端 admin.playedu.xyz（演示数据每小时整点重置） |
| 定位 | 面向企业内训的私有化培训平台，强调部门—学员—课程的组织化培训 |

## 2.2 选择依据

选择 PlayEdu 作为首要参照，理由集中在四点：

1. **数据模型与本平台同构度最高**。它的组织方式是“分类 → 课程 → 课时”，课程带必修/选修属性，学员带学习进度与学习时长，几乎就是本平台第 6 章数据模型的一个已验证版本。对照自身设计时，可以直接判断哪些字段是必备的、哪些是冗余的。
2. **技术栈最接近约束规范**。前端 React 18 + 前后端分离 + 独立 API，与本平台“React + TypeScript + Vite + Ant Design”的约束在同一范式内，交互与工程组织可复用；而酷瓜与 Moodle 都是服务端模板渲染，参考价值集中在业务而非前端。
3. **同时具备学员端与管理端**，可以完整观察“内容生产—上架—学习—进度回传”的闭环，而不是只看学习侧。
4. **演示环境可用**。演示账号公开、页面可交互、数据每小时重置，适合做可复现的界面比对（采集方式见附录 A）。

[IMG:fig2_1.png] 图 2-1 学员端首页：课程进度、学习时长与课程卡片

首页把“我学得怎么样”放在最上方，是本项目最值得借鉴的一处设计。左上卡片用“必修课 0/4、选修课 0/2”回答完成情况，右上用“今日 0 分钟 / 累计 12 分钟”回答投入程度，两者都不需要点进任何页面即可获得。课程卡片右下角直接展示进度百分比与进度条（图 2-1 第二行最右侧一张为 75%），把“继续学习”的入口和数据合成一体。

对本平台的启示：FR-STU-02 规定了“继续学习”区域，但未明确必修与选修的区分。PlayEdu 的必修/选修概念与实训工坊的“前置必修”在语义上并不相同（前者是培训计划内的必学，后者是项目准入条件），若照搬会造成学生误解，建议本平台只保留“来自外部平台的学习要求”提示，不引入课程自身的必修属性。

[IMG:fig2_2.png] 图 2-2 课程详情：课时清单与课时完成状态

课程详情页的信息密度控制得较好：左侧课程信息与目录，右侧一个 75% 的环形进度，课时行末用文字标注“已学完 / 开始学习”，不依赖图标。这种“状态用文字而非颜色表达”的做法在警院场景下更稳妥——投影与打印都不失真。

需要指出的是，它的课程目录是**扁平课时列表**，没有章节分组（本平台第 6 章设计了 chapter 与 lesson 两层）。当课时数超过 20 时，扁平列表的检索效率会明显下降，这也是本平台保留章节层的直接理由。

[IMG:fig2_3.png] 图 2-3 视频课时播放：播放器与防录屏水印

画面中那条半透明的“PlayEdu演示账号1 1@playedu.xyz”是播放器叠加的动态水印，用于追溯录屏泄露来源。这一能力在本平台需求文档中未被显式要求，但对警务类教学资源有现实意义，建议作为 NFR-SE 的补充项纳入：水印内容取全局 userId，位置随时间漂移，不遮挡主画面。

同时也暴露了一个问题：该页除播放器外没有任何导航，学生想切换课时必须“返回课程”再点下一节。本平台 FR-STU-06/07 要求“章节内课时可上一节/下一节连续切换”，正是针对这一体验缺口。

[IMG:fig2_4.png] 图 2-4 管理端课程中心：课程列表与上架状态

列表字段包括课程名称、课程分类、指派部门、必修/选修、创建人、上架时间。注意这里只有“上架时间”，没有“状态”列——因为该系统不存在草稿/待审核/已发布的状态区分，课程创建即上架。这与本平台 FR-TEA-05 与 3.3 节的状态机存在本质差异：**PlayEdu 把审核权交给了流程外的人（谁有账号谁发布），本平台要求“对外可见的每一门课程都经过人工审核”**。这是不可妥协的差异，也说明审核流必须自研。

另一处值得注意的是“指派部门”字段：它把课程可见范围绑定到组织结构，本平台没有部门概念（组织关系由论坛持有），因此不需要该字段，可见性统一由“已发布即全员可见”处理。

[IMG:fig2_5.png] 图 2-5 管理端分类管理：分类的新增与排序

分类管理提供了新建、拖拽排序、改名、删除四种操作，交互简洁。但它是**单级分类**，而本平台在 6.2.1 中预留了 parentId 以支持两级分类——考虑到七大类下可能出现“网络安全/Web 安全、网络安全/渗透测试”这样的细分，两级结构更合适。参考该界面时，应在树形控件上做扩展，而不是照搬平铺列表。

## 2.4 主要特点

| 特点 | 说明 | 对本平台的价值 |
|---|---|---|
| 组织化培训模型 | 部门—学员—课程三层指派，支持按部门批量授权 | 本平台无部门概念，可忽略；但“按人群授权”的思路可用于后续按年级/班级开放课程 |
| 课时级进度追踪 | 记录每个课时的学习状态，汇总为课程进度 | 与本平台 lesson_progress → learning_progress 的派生关系一致，可交叉验证判定逻辑 |
| 必修/选修划分 | 课程带必修属性，首页单独统计完成数 | 概念可用，但需与本平台的“前置必修”区分，避免语义混淆 |
| 视频私有化存储 | 视频不暴露源地址，播放走签名地址 | 与本平台 NFR-SE-07 的要求一致，可作为实现参考 |
| 多端一致 | PC、H5、管理后台共用一套 API | 与本平台“独立 API + 多端”的结构一致 |
| 演示数据可重置 | 每小时重置，适合反复比对 | 便于评审现场复现 |

## 2.5 局限与二次开发点

| 缺口 | 影响 | 建议 |
|---|---|---|
| 无审核状态机 | 无法满足 3.3 节的发布审核流程 | 自研；在课程表上增加 status、lockVersion，并按 3.3.3 的状态迁移实现 |
| 无笔记与收藏 | 缺 FR-STU-09/10/11 | 自研；笔记按“课程 + 可选课时”挂载，收藏做唯一键幂等 |
| 无开放接口与事件 | 无法支撑工坊、考试平台、成长档案的取数 | 自研 `/open/v1/` 与 course.completed 事件，参考第 7 章与附录 B |
| 认证为本地账号 | 与本平台“不自建账号”冲突 | 替换为论坛 OIDC，本地仅保留 userId 映射 |
| 单级分类 | 七大类细分受限 | 增加 parentId，树形管理 |
| 课程无版本概念 | 已发布课程修改会直接影响在线内容 | 引入 version 与完成基线锁定（见 3.4.4） |
