# 4 项目三：Moodle

## 4.1 项目概览

| 项目 | 内容 |
|---|---|
| 项目名称 | Moodle（Modular Object-Oriented Dynamic Learning Environment） |
| 代码仓库 | https://github.com/moodle/moodle |
| 开源许可 | GPL-3.0 |
| 技术栈 | PHP + MySQL/PostgreSQL，Mustache 模板，jQuery 与原生 JS 混合 |
| 部署形态 | LAMP/LNMP，全球数千所院校在用，插件生态庞大 |
| 演示环境 | school.moodledemo.net（Mount Orange 示范大学，含学生/教师/管理员/院长多角色账号，每小时重置） |
| 定位 | 通用学习管理系统，以“课程 + 活动 + 完成跟踪 + 评价”为核心 |

## 4.2 选择依据

Moodle 在产品形态上与本平台差异很大——它更重、更学院派、功能远超本平台边界。之所以仍纳入比对，是因为它解决了一个本平台必须回答的问题：**“学习进度”到底应该以什么为最小单位**。

本平台当前的设计是“课时完成即进度”，判定标准是覆盖率 95% 与滚动 90%。Moodle 的答案是“活动完成”（Activity completion）——课程由若干活动组成（阅读、讨论、作业、测验、图书），每个活动可配置完成条件（查看即完成、需提交、需评分通过），教师可按活动查看全班完成矩阵。这一模型比“课时看完”更细，也更能支撑“是否真的学过”的判断。

此外，Moodle 的示范站点提供了完整的多角色账号体系，是唯一能在一个站点内同时观察学生视角、教师视角与管理视角的项目，适合用来校验本平台第 8 章权限点清单是否有遗漏。

[IMG:fig4_1.png] 图 4-1 我的课程：完成百分比、星标与课程类别

这一屏包含三个对本平台有直接价值的细节：

其一，卡片底部以“42% 已完成”的纯文本表达进度，不加进度条。对比 PlayEdu 的进度条 + 百分比，Moodle 的做法在列表密度高时更清晰；本平台在移动端应采用进度条（触屏需要视觉锚点），在桌面端列表可采用纯文本。

其二，“星标”（图中 Psychology in Cinema 标题前的星形）就是本平台的“收藏”，但它的语义更强——星标同时影响“我的课程”的排序与筛选。本平台 FR-STU-09 只要求收藏列表，若把收藏与排序联动，可以提升复用率。

其三，课程类别直接显示在卡片上（Faculty of Health and Medicine），说明分类是课程的一等属性而非附属标签。本平台七大类是硬约束，更应在卡片上显性展示，便于学生快速判断课程归属。

[IMG:fig4_2.png] 图 4-2 课程页：章节导航、活动列表与完成状态

课程页是 Moodle 的典型三栏结构：左侧章节大纲（可折叠，带完成状态圆点）、中部活动列表（每个活动右侧有“标记完成”或“待办事项”下拉）、右侧课程信息块。

值得借鉴的是**完成状态的三种表达**：左侧大纲用空心圆（未完成）与实心圆（已完成）表示，中部用“标记完成”按钮表示可手动确认，活动行本身还有完成条件说明。本平台目前只有“未开始/学习中/已完成”三态，粒度偏粗；若引入“课时内活动”的概念，可以表达“看过但未提交”这类中间状态。

不建议照搬的是信息层级：Moodle 把课程设置、参与人、成绩、活动、更多全部平铺在课程标题下方，教师需要多步才能找到“编辑”入口。本平台 FR-TEA-02 要求编排操作直接可达，应避免这种层层下钻。

[IMG:fig4_3.png] 图 4-3 教师视角：编辑模式下的章节与活动编辑

开启“编辑模式”后，每个章节与每个活动右侧出现铅笔图标，章节标题旁出现“编辑”文字按钮，顶部提供“批量操作”。这种“全局开关 + 就地编辑”的模式，比“进入独立编辑页”更贴近教师的实际心智：教师通常在浏览课程时发现要改的地方，就地编辑的路径最短。

本平台 FR-TEA-02 的编排需求（增删章节、调整顺序、设置类型）适合采用同样思路：课程详情页对责任教师显示编辑开关，开启后行内出现操作入口，拖拽排序，保存即生效（草稿态）。

[IMG:fig4_4.png] 图 4-4 活动进度报告：学生与活动的完成矩阵

这是三个项目中最接近“学习数据可观测”目标的一屏。表格纵向是学生（含邮箱），横向是课程内的每一个活动，交叉点用图标表示完成状态（已完成/未完成/未开放），表头是活动名称与日期。

对本平台的直接启示有两点：

第一，FR-TEA-09 当前只要求“课时流失分布（到达人数/完成人数）”，属于聚合视角；而教师真正需要的是“谁卡在哪一节”。矩阵视图虽然涉及个人明细，但可以裁剪为“按课时聚合 + 可下钻到名单”，下钻行为记入审计。这一点需要在隐私与可用性之间做取舍，本平台当前选择“不展示个人明细”，理由是避免与工坊成员管理重叠——这个理由成立，但可以补充“课时级到达率”作为折中。

第二，这张表本质上就是本平台 `lesson_progress` 表的透视结果。说明只要课时级进度采集准确，课程级、班级级、平台级的任何视图都可以事后生成，**采集粒度决定了分析上限**。本平台已把 lesson_progress 设为事实表，方向正确。

## 4.4 主要特点

| 特点 | 说明 | 对本平台的价值 |
|---|---|---|
| 活动完成模型 | 完成条件可按“查看/提交/评分”配置，粒度细于课时 | 提示本平台“课时完成”粒度过粗，可预留活动层 |
| 完成矩阵报告 | 学生 × 活动 的完成情况一屏可见 | 为 FR-TEA-09 提供更强形态 |
| 星标即收藏 | 星标影响列表排序与筛选 | 可增强 FR-STU-09 |
| 多级课程类别 | 类别可嵌套，课程必属一类 | 印证两级分类设计 |
| 编辑模式 | 全局开关 + 就地编辑 | 可作为 FR-TEA-02 的交互范式 |
| 插件生态 | 认证、 enrollment、报表均可插拔 | 说明“能力可插拔”的架构价值，但本平台不宜引入插件机制 |

## 4.5 局限与二次开发点

| 缺口 | 影响 | 建议 |
|---|---|---|
| 功能远超边界 | 含测验、作业、成绩、证书、论坛、徽章 | 与本平台 2.5.2 边界红线直接冲突，不可作为底座 |
| 界面陈旧、层级深 | 与学生端“轻量学习”的定位不符 | 仅借鉴信息结构，不复用交互 |
| PHP 模板渲染 | 与 React 技术栈不兼容 | 不复用前端代码 |
| 无覆盖率概念 | 无法满足 FR-STU-07 的 95% 覆盖率判定 | 自研播放器与埋点 |
| 无 OIDC 原生支持 | 需插件桥接论坛 SSO | 自研，参考 2.2 节约束 |
| 体量与运维成本 | 部署、升级、插件维护成本高 | 不纳入技术选型 |
